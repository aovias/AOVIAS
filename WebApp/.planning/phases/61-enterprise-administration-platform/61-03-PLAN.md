## The cutover pattern

"Nothing should remain hardcoded" is the goal; "no regression" is the constraint. They are
satisfied together only by cutting over one domain at a time, in four steps:

1. **Seed** configuration that reproduces today's behaviour exactly.
2. **Switch** the read path from the hardcoded value to the configuration.
3. **Verify** output is byte-identical to before the switch, on real data.
4. **Release** the configuration to diverge, behind the feature flag from sub-wave 02a.

A cutover that skips step 3 is not a cutover; it is a rewrite with an untested hypothesis.
Every domain below follows all four steps, and each is independently revertible by its flag.

## Cutover order

Ordered by blast radius, smallest first.

### 03a — Severity
Replace hardcoded severity labels, colours, and ordering with the severity-definition table
from 02b. Enum values remain the storage primitive (research §3.5). Consumers: findings,
deficiencies, incidents, gaps, recommendations, and every WebApp badge component.

### 03b — Risk
Point `RiskRegisterAppService`'s matrix construction at the configured matrix and formula
(research §3.4). Replaces the fixed `for 1..5` loops and `score = likelihood * impact`.

**Explicitly out of scope**, and to be documented as such: `journey.CalculateRiskScore(major, minor)`
(`ComplianceJourneyService:1191`, `ComplianceEscalationJob:145`), the NABH 0–100 accreditation
score (`DeterministicNabhScoringService:192`), and `ControlCenterAggregationService:456`.
These are **different quantities** that happen to share the name "risk score". Collapsing them
into the register matrix would be a behavioural regression, not a de-hardcoding.

### 03c — Notifications and Approvals
Notification dispatch consults configured reminder, escalation, and digest rules. Approval
requests resolve their chain from configured approval definitions rather than call-site logic.

### 03d — Workflow
Migrate `AuditSessionClosedWorkflowRule` and `EvidenceApprovedWorkflowRule` to
`ConfiguredWorkflowRule` instances — one at a time, each verified identical before the next.
`WorkflowRuleEngine` and `WorkflowRuleEngineTests` are not modified (research §3.3).

### 03e — Programs and Templates
Planning consumes configured Programs. Audit creation consumes configured Templates.
Both are additive: today nothing consumes them, so there is no behaviour to preserve — only
behaviour to add.

### 03f — AI and Security
AI behaviour follows configured prompt templates, policies, knowledge sources, allowed models,
confidence thresholds, and privacy settings. Security follows centralised Identity
configuration.

## Audit Workspace integration

Each lifecycle stage consumes administration configuration:

| Stage | Consumes |
| --- | --- |
| Planning | Programs, Templates, Department structure |
| Execution | Workflow, Templates, Mandatory activities |
| Evidence | Evidence templates, Retention, Storage policies |
| Findings | Severity matrix, Finding templates, Notification rules |
| CAPA | CAPA templates, Approval chains, Escalation thresholds |
| Verification | Workflow transitions, Validation rules |
| Closure | Approval engine, Digital signatures |
| Reports | Report templates, configured KPIs, Number sequences |

Deliver stage by stage, verifying the lifecycle end to end after each.

## Context Drawer

Extend the Plan 01 wiring so the drawer exposes, per context: Related Policies, Workflow
Configuration, Approval Status, Risk Rules, Templates, AI Guidance, Configuration History,
Relevant Documents. Configuration History requires an audit trail on configuration changes —
confirm 02a captured it, and add it there if not.

## Executive Intelligence

Analytics consume configured Risk Matrix, Severity, Workflow, KPIs, Department structure,
Programs, and Templates. Note the 03b scope boundary: the NABH accreditation score is a
distinct model and is not governed by the register risk matrix unless a separate decision
says otherwise.

## Runtime validation

Full lifecycle — Planning → Execution → Evidence → Findings → CAPA → Verification → Closure →
Reports — driven **only** by configured administration settings, on a fresh database seeded
from administration, with no hardcoded fallback reachable.

Then repeat with a **deliberately non-default** configuration: a 4×6 risk matrix, a renamed
severity level, an extra approval level. If the lifecycle adapts, the platform is
configuration-driven. If it does not, something is still hardcoded — and that is the actual
test of Stage 5's Definition of Done.
