# Phase 56 — Plan 01: Documented HTTP budget & long-read client policy

## Phase goal (backward)

After this wave, **long-running Journey read endpoints** use an **explicit, documented** client timeout that is **≥** the agreed Gateway/API chain (or “no artificial client deadline” if the chain is unlimited), implemented via **`HttpContext`** so **short global defaults** (if introduced later) **never** apply accidentally to `GET .../chapters/{id}/standards` and sibling Journey GETs. Cross-link **SLA/limits** in `docs/backend/journey-screen-api-spec.md` (placeholder section if numbers come from Gateway repo only).

## must_haves

- [ ] `environment` exposes a **named constant** (e.g. `journeyLongReadTimeoutMs`) sourced from a **single** place; prod/staging values documented in one line (or `0` / `undefined` = use browser/stack default only — **documented**).
- [ ] `HttpContext` token(s) mark Journey **session / dashboard / chapters index / chapter standards / objective element** GETs as **long-read**; interceptor applies `timeout` **only** when context is set and milliseconds are positive (skip timeout when `0` / unset).
- [ ] `JourneyDataService` passes context on all **aggregation-heavy** GETs listed in the phase prompt; **mutations and small** GETs remain unchanged unless they share the same backend SLA.
- [ ] No new **stricter** default for **all** HTTP traffic — scope is Journey long-reads only.
- [ ] `ng build` passes.
