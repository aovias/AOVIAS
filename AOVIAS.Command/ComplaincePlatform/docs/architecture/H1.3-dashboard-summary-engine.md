## Purpose

Introduce a dedicated **Dashboard Summary Engine** in ComplianceService that serves Phase 1 KPIs from lightweight reads (`ComplianceSnapshots` + task/finding aggregates) with scoped caching and telemetry. The H1.1 **PramanDashboardProvider** now uses this engine for the experience path.

**Non-goals:** No changes to `DashboardSnapshotService`, legacy `GET /dashboard/summary`, or snapshot HTTP endpoints.

---

## Responsibilities vs Snapshot Service

| Component | Role | Path |
|-----------|------|------|
| **DashboardSummaryEngine** | Phase 1 KPIs (score, tasks, alerts, active journeys) | `GET /platform/dashboard/experience` |
| **DashboardSnapshotService** | Full program-overview snapshot (framework trees, trends, activity lists) | Existing snapshot endpoints (unchanged) |

The experience layer (H1.2) calls the Summary Engine via the provider registry. The Angular shell still loads the legacy snapshot in the background for Phase 2+ widgets.

---

## Data ownership

- **Score:** Latest `ComplianceSnapshots.OverallScore` per active journey/framework (maintained by `ComplianceSnapshotProjector` / `ComplianceFrameworkSnapshotRecalculationService`). **Fallback** to `IComplianceScoreService.GetHospitalScoreAsync` / `GetFrameworkScoreAsync` only when no snapshot row exists (cold hospital).
- **Tasks:** Single `COUNT` of non-completed tasks for hospital (optional framework filter via standard/chapter join).
- **Alerts:** Correlated join on unresolved audit findings (`FindingScope.Audit`, `!IsResolved`) — no materialized journey ID lists.
- **Active journeys:** Count where lifecycle state is in the active set (matches `DashboardSnapshotService` semantics).
- **Recent activity:** `MAX(ChangedAt)` on `ComplianceJourneyHistories` (scalar, not full activity list).

The engine does **not** call `AggregationService.ComputeFrameworkAsync` or `GetJourneySummaryAsync`.

## Cache

| Setting | Value |
|---------|-------|
| **Key** | `dashboard-summary:{tenantId}:{hospitalId\|all}:{frameworkId\|all}` |
| **Invalidation** | Version bump per scope key (pattern from `FrameworkCatalogMemoryCache`) |
| **TTL** | 60 seconds (safety net if invalidation missed) |
| **Acceptable staleness** | Typically &lt;60s; worst case until next snapshot recalc + TTL |

### Invalidation triggers

| Trigger | Hook |
|---------|------|
| Snapshot recalculated | `ComplianceFrameworkSnapshotRecalculationService.RecalculateAsync` (after success) |
| Score / deficiency / obligation outbox | `InProcessOutboxProcessor` (after successful handling) |
| Task complete | `ComplianceCommandService.CompleteTaskAsync` (after commit) |
| Journey lifecycle transition | `ComplianceJourneyService.TransitionJourneyAsync` (after commit) |

---

## Refresh lifecycle

| Mechanism | Behavior |
|-----------|----------|
| Login / experience load | Cache miss → engine query |
| Manual refresh | Client `forceRefresh=true` → Gateway → ComplianceService bypasses cache once |
| Context switch | Different cache key |
| Periodic client refresh | Hits warm cache |
| Event invalidation | Next request recomputes |

---

## Telemetry

`DashboardSummaryTelemetry` records: `ContextResolutionMs`, `CacheLookupMs`, `CacheHit`, `QueryExecutionMs`, `CachePopulationMs`, `TotalMs`.

- Logged at Information when `TotalMs > 200`
- Optional dev header: `X-Dashboard-Summary-Timing` (JSON) when `DashboardSummary:ExposeTimingHeaders=true` or in Development
