# Phase 61 — Plan 01 — Stage 5A: Enterprise Administration Foundation

> Depends on: `61-RESEARCH.md`.
> Repository: `WebApp` only. No backend changes in this wave.
> Principle for this wave: **integrate what exists, scaffold what does not, delete nothing.**

---

## Objective

Turn the existing Administration Center into the single Enterprise Administration Workspace
with the twelve required tabs, a shared workspace experience, and no duplicate administration
pages — using existing services and existing UI primitives wherever they exist.

## Non-goals

- No new schema, no new backend endpoints, no migrations (that is Plan 02).
- No removal of operational features. `/app/risks`, `/app/frameworks` etc. keep working.
- No behaviour change to the audit workspace (that is Plan 03).

---

## Target information architecture

Twelve tabs, in this order, replacing the current eight sections:

| # | Tab | Route base | Composition |
| --- | --- | --- | --- |
| 1 | Organization | `settings/organization` | existing `general/organization`, `general/branding` + new scaffolds |
| 2 | Programs | `settings/programs` | scaffold (backend thin — see Plan 02) |
| 3 | Templates | `settings/templates` | scaffold |
| 4 | Frameworks | `settings/frameworks` | fold administrative surface of `features/frameworks` |
| 5 | Risk | `settings/risk` | scaffold (configuration only; register stays at `/app/risks`) |
| 6 | Workflow | `settings/workflow` | scaffold |
| 7 | Notifications | `settings/notifications` | existing, unchanged |
| 8 | Approvals | `settings/approvals` | scaffold |
| 9 | Teams | `settings/teams` | existing `workforce-admin`, re-labelled |
| 10 | Security | `settings/security` | existing `identity/*` + fold `access-governance`, `security` |
| 11 | AI | `settings/ai` | existing, unchanged |
| 12 | System | `settings/system` | existing `platform/*`, `system/audit`, `theme`, `about` regrouped |

Rule: **every route that exists today keeps working.** New paths are added; old paths become
redirects using the established `legacyAdminRedirect` / `redirectTo` patterns.

## Step 1 — Shared workspace primitives

`src/app/shared/ui/administration/`

1. **`AdminToolbarComponent`** (`admin-toolbar.component.ts`) — the shared toolbar every tab
   uses. Content-projected slots: title/subtitle, search, filters, actions. OnPush.
   Token-only styling per `DESIGN_RULES.md`; no hex/rgba.
2. **`AdminFilterBarComponent`** (`admin-filter-bar.component.ts`) — declarative filter
   chips/selects driven by a `AdminFilterDefinition[]` model, emitting a typed change.
3. Re-export both from `index.ts` alongside the existing four components.
4. Reuse — do **not** duplicate: `AdminPageStateComponent` (loading/empty/error),
   `AdminSectionCardComponent`, `AdminStatCardComponent`, `AdminStatusChipComponent`,
   `WorkspaceSearchComponent`, `admin-layout.css`.

**Acceptance:** a tab can be built from toolbar + filter bar + section cards + page state
without writing tab-specific layout CSS.

## Step 2 — Context Drawer in the administration shell

`ContextDrawerService` / `ContextDrawerComponent` already exist and are tested.

1. Render `<app-context-drawer>` in `AdministrationShellComponent`.
2. Each tab publishes its context through `ContextDrawerService` on activation.
3. In this wave the drawer surfaces what is locally knowable — current scope (organization /
   hospital), the tab's configuration summary, and links. Policies, workflow configuration,
   approval status, risk rules, and AI guidance arrive in Plan 03.

**Acceptance:** drawer opens on every administration tab; closes without layout shift; no
duplicate drawer instance when navigating between tabs.

## Step 3 — Navigation model

`src/app/features/settings/models/settings-nav.model.ts`

1. Replace `getSettingsNavSections()`'s eight sections with the twelve tabs above.
2. Keep the `SettingsNavItem` contract as-is — `icon`, `disabled`, `comingSoon`, `exactMatch`
   are all needed. Scaffolded tabs use `comingSoon: true` on items whose backend lands in
   Plan 02.
3. Update `getSettingsHomeCards()` to twelve cards matching the tabs, with honest `footer` /
   `status` values (`configured` only where the tab is genuinely backed).
4. Introduce a `SETTINGS_BASE`-derived constant per tab so route strings are declared once.

**Acceptance:** nav renders twelve tabs; `comingSoon` items are visually distinct; no tab
label is a lie about its state.

## Step 4 — Routes

`src/app/features/settings/routes.ts`

1. Add the six new route bases (`programs`, `templates`, `frameworks`, `risk`, `workflow`,
   `approvals`) plus the regrouped `organization`, `teams`, `security`, `system`.
2. Add in-workspace redirects preserving every current path:
   - `general/organization` → `organization/profile`
   - `general/branding` → `organization/branding`
   - `identity/users` → `security/users`
   - `identity/password` → `security/password`
   - `workforce/*` → `teams/*`
   - `platform/licensing` → `system/licensing`, `platform/commercial` → `system/commercial`,
     `platform/compliance` → `system/compliance-defaults`,
     `platform/integrations/*` → `system/integrations/*`
   - `system/audit` → `system/audit` (unchanged)
   - existing legacy redirect blocks stay untouched.
3. `app.routes.ts` — add `legacyAdminRedirect` entries folding `/app/access-governance` and
   `/app/security` administrative paths into `/app/settings/security`. **Decision required
   before folding `/app/frameworks` and `/app/risks`** — see Open Questions.
4. Preserve `permissionGuard` and `settingsDirtyGuard` on every route that has them today.

**Acceptance:** every URL reachable before this wave is still reachable after it. Verified by
enumerating current paths and navigating each.

## Step 5 — Tab scaffolds

For each of Programs, Templates, Risk, Workflow, Approvals, and the new Organization
sub-pages, create a page component that:

- uses `AdminToolbarComponent` + `AdminPageStateComponent`,
- renders a `AdminPageStateKind` of `empty` with copy naming the capability and its status,
- is routed and reachable,
- carries **no** mock data presented as real.

An empty state that says a capability is not yet configurable is honest. A table of invented
rows is not. Scaffolds show the former.

**Acceptance:** each scaffold is reachable, uses shared primitives only, and states its
actual status.

## Step 6 — Frameworks administration

`features/frameworks` is an operational workspace. This step surfaces its **administrative**
capabilities (frameworks, chapters, standards, objective elements, version management,
activation, cross mapping) inside the workspace, bound to the existing `FrameworkController`
/ `FrameworkReadController` APIs via the existing frameworks services.

Reuse the existing framework data services; do not create a parallel client.

**Acceptance:** framework list and hierarchy render inside the administration workspace from
the live API, with loading and error states from `AdminPageStateComponent`.

## Step 7 — Verification

1. `npm run build` (or `ng build`) clean. Note: production build may fail on the
   **pre-existing** SCSS budget documented in `57-VERIFICATION.md` — that is not a regression
   introduced here, and must be reported as pre-existing if hit.
2. Dev server; navigate all twelve tabs.
3. Enumerate and navigate every pre-existing administration URL; confirm no 404 and no
   redirect loop.
4. Light/dark theme pass on the shell and two representative tabs.
5. Write `61-01-SUMMARY.md`.

## Open questions — require a decision before Step 4.3 completes

1. **Frameworks.** Fold `/app/frameworks` entirely into administration, or split — operational
   browsing stays at `/app/frameworks`, configuration moves to `settings/frameworks`?
   *Recommendation: split.* Auditors browse frameworks daily; that is not an administrative act.
2. **Risk.** Same question for `/app/risks`. *Recommendation: split.* The risk **register** is
   operational; the risk **matrix, formula, levels, and thresholds** are administration.
3. **Governance.** `/app/governance` (`GOVERNANCE_ROUTES`) was not named in the Stage 5 tab
   list. Leave as-is this wave, or fold into System? *Recommendation: leave, and revisit in
   Plan 03* when configuration consumers are known.

These three do not block Steps 1, 2, 3, 5, 6, or 7.
