# Phase 61 — Plan 02 — Stage 5B: Enterprise Administration Expansion

> Depends on: Plan 01 (workspace + shared primitives + scaffolds in place).
> Repositories: `ComplaincePlatform` (schema, services, controllers, Gateway) + `WebApp` (clients, UIs).
> This is the largest wave and is split into sub-waves 02a–02f, each independently shippable.

---

## Governance rules — apply to every sub-wave

Non-negotiable, from `ENGINEERING_STANDARDS.md` §1 and the Stage 5 engineering rules:

1. Migrations are **generated**: `dotnet ef migrations add <Name>`. Never authored by hand.
   Edit only after generation.
2. Never run `dotnet ef migrations remove` in ComplianceService. Delete files manually and
   restore the snapshot from git.
3. After every migration: `pwsh scripts/ci/validate-migrations.ps1` — must pass all three
   gates (attributes present, no snapshot drift, fresh DB builds).
4. A newly generated migration on top of the sub-wave's own migration must produce **zero
   operations**. If it does not, the model and snapshot disagree — stop and reconcile.
5. Fresh-database validation and existing-database upgrade validation per sub-wave.
6. **No unrelated operations in a migration.** ComplianceService's history is polluted with
   these; do not add to it.

Per-domain delivery slice (repeat for each domain):
entity + configuration → generated migration → repository/service → controller → Gateway
route → typed Angular client → replace the Plan 01 scaffold with a real UI → tests.

## Sub-wave 02a — System Configuration *(do this first)*

Everything else wants number sequences, feature flags, and defaults. Building it first means
later sub-waves consume it instead of inventing their own.

- Number Sequences, Retention, Feature Flags, Backup Policies, Storage Policies, Integration
  Settings, License Settings, Default Values.
- Feature flags are the rollback mechanism for every subsequent Stage 5C cutover. This is the
  reason for the ordering.
- UI replaces the `system/*` scaffolds from Plan 01.

## Sub-wave 02b — Risk and Severity Administration

**Risk.** Risk Categories, Likelihood Matrix, Impact Matrix, Risk Formula, Risk Levels,
Heat Maps, Residual Risk, Acceptance Rules, Escalation Thresholds.

Constraint from research §3.4: `RiskRegisterAppService` hardcodes a 5×5 loop and
`score = likelihood * impact`. The configuration must support an N×M matrix and a
declarative formula, and must **seed to exactly 5×5 / multiply** so behaviour is unchanged on
day one.

**Severity.** Critical, Major, Moderate, Minor, Observation, Opportunity for Improvement,
each with business, reporting, workflow, and notification rules.

Constraint from research §3.5: six severity enums exist and are persisted as ints across many
tables. **Do not replace the enums.** Introduce a severity-definition table keyed by the
existing enum value, supplying label, colour, order, and the four rule sets. Configurability
without a destructive data migration.

## Sub-wave 02c — Workflow Administration

Lifecycle, Transitions, Validation Rules, Parallel Flows, Conditional Flows, Mandatory and
Optional Activities, Auto Progression, Workflow Versioning.

Constraint and opportunity from research §3.3: `WorkflowRuleEngine` already resolves
`IEnumerable<IWorkflowRule>` from DI and dispatches on `EventType`. Add a
`ConfiguredWorkflowRule` built from persisted configuration and registered into the same
collection. The engine, its interface, and `WorkflowRuleEngineTests` stay untouched. The two
compiled rules (`AuditSessionClosedWorkflowRule`, `EvidenceApprovedWorkflowRule`) migrate to
configuration one at a time in Plan 03, each verified to produce identical behaviour first.

Leave `AIOrchestratorService`'s separate workflow engine alone — it serves AI autonomy, not
the audit lifecycle, and no Stage 5 deliverable requires unifying them.

## Sub-wave 02d — Approval Engine and Digital Signatures

**Approvals.** Single-Level, Multi-Level, Parallel, Conditional, Delegation, Escalation,
Approval History. Genuinely new schema — research §3.6 found only
`AccessGovernanceService.ApprovalAuthority` and document-scoped `DocumentApproval`. Decide
whether the generic engine lives in ComplianceService or AccessGovernanceService; the
existing `ApprovalAuthority` aggregate argues for the latter, the consumers argue for the
former. **Resolve before writing the migration.**

**Digital Signatures.** Electronic Signatures, Approval Certificates, Identity Verification,
Timestamp, Audit Trail, Non-Repudiation. Non-repudiation has legal weight in an accreditation
context: the signature payload must bind signer identity, the exact artefact version, and a
trusted timestamp. Specify the payload and hashing scheme in writing before implementing.

## Sub-wave 02e — Annual Audit Programs

Annual, Quarterly, Monthly, Risk-Based, and Department Programs; Program Approval, Coverage
Tracking, Progress Monitoring, Automatic Audit Generation.

Constraint from research §3.2: `ComplianceProgram` already exists (thin — `HospitalId`,
`ComplianceFrameworkId`, `Name`, `Explainability`) with `V1/ProgramsController` exposing
`POST`, `GET {programId}`, `GET` at `api/v{version}/compliance/programs`. **Extend this
aggregate.** Introducing a second "program" concept would leave two competing meanings in one
service.

Automatic Audit Generation depends on the scheduling surface — check `AuditScheduleController`
and Hangfire job registration before designing it.

## Sub-wave 02f — Template Library and Notification Center completion

**Templates.** Audit, Checklist, Evidence, Finding, CAPA, Report, Notification, and Workflow
templates, with Versioning, Approval, Clone, Import, Export.

Notification templates already exist under `settings/notifications/templates` — the library
must **reference** them, not fork them. One template concept per artefact type.

**Notifications.** The existing 8-page admin covers Email/SMS/Push/In-App, templates,
channels, providers, queues, history, preferences, subscriptions. Remaining: Reminder Rules,
Escalation Rules, Digest Notifications, and business rules binding notifications to severity
and workflow configuration.

## Exit criteria for Plan 02

- Ten administration domains operational, each replacing its Plan 01 scaffold.
- Every migration generated, deterministic, and zero-drift under `validate-migrations.ps1`.
- Fresh DB and existing DB both validated after the final sub-wave.
- Every domain seeded with configuration that reproduces **current** behaviour, so Plan 03
  can cut over without behaviour change.
- `61-02-SUMMARY.md` per sub-wave.
