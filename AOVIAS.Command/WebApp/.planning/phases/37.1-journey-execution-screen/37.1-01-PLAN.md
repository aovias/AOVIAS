# 37.1-01: Execution route, container shell, and viewport layout foundation

## Objective
Create a brand-new Journey Execution page entry point and container shell with a strict three-column workspace contract (left navigation, center work area, right action context), including a back-to-main-journey action and panel-level scrolling/sticky headers.

## Tasks

<task id="01" name="Add execution route and navigation handoff">
- Add a dedicated execution route under Journey feature (e.g., `/app/journey/execution` or equivalent existing route pattern).
- Wire **Continue Journey** action from Journey dashboard to open this new execution screen.
- Add explicit back navigation control from execution screen to main Journey screen.

**must_haves:**
- Back button exists and is keyboard accessible.
- Route remains lazy-loaded under existing Journey feature boundaries.
</task>

<task id="02" name="Create execution container and typed panel contracts">
- Create a new execution page container component (standalone + OnPush).
- Add typed view models for:
  - chapter navigation panel
  - standards panel
  - selected OE/action panel
- Keep business/data mapping in container/store adapters only.

**must_haves:**
- No `any` in new execution VM contracts.
- Child panel inputs are serializable and presentation-ready.
</task>

<task id="03" name="Implement 3-column viewport layout contract">
- Build full-height execution workspace layout using tokenized grid/flex primitives.
- Enforce column intent:
  - left ~25%
  - center ~50%
  - right ~25%
- Each panel has independent vertical scroll and sticky local header.

**must_haves:**
- No inline styles in execution template.
- No raw hex/px in execution page SCSS.
- Mobile/tablet collapse preserves logical panel priority.
</task>

## Verification criteria
- [ ] Execution route renders a new page (not reused legacy layout).
- [ ] Continue Journey opens execution screen and back action returns correctly.
- [ ] Three-column workspace and independent panel scrolling are implemented.
- [ ] Container orchestrates state; no business logic in UI child components.

## must_haves (goal-backward)
- A stable mission-control shell exists for data-heavy compliance execution.
- Navigation into/out of execution flow is clear and reversible.
