## Objective

Implement route-level enforcement for both authentication and onboarding completion across the app.

**Important scope boundary (exclude already implemented in Phase 21):**
- ✅ Already done: login-time org-detail fetch, post-login redirect decision, API-driven header hospital selector.
- ❌ Still needed: guard-based enforcement for deep links, refresh, back/forward navigation, and protected lazy routes.

<task>
  <name>Create onboarding guard as second protection layer</name>
  <files>src/app/core/guards/onboarding.guard.ts, src/app/core/services/organization.service.ts</files>
  <action>
    1. Add new functional `onboardingGuard` that runs after `authGuard`.
    2. Guard behavior:
       - Load org details from `OrganizationService` cache first; call API only if missing.
       - Evaluate `hospitals[].isOnboarded`.
       - If no onboarded hospital, redirect to `/onboarding`.
       - If any onboarded hospital exists, allow navigation.
    3. Failure behavior:
       - If org-detail fetch fails, redirect to a safe route (prefer onboarding) and log warning.
    4. Add helper in `OrganizationService` to avoid duplicate in-flight org-detail calls (request sharing/caching) so guards don’t spam API on rapid route changes.
  </action>
  <verify>
    - Logged-in user with no onboarded hospital is always redirected to onboarding
    - Logged-in user with onboarded hospital is allowed through
    - Rapid navigation does not trigger repeated org-detail calls
  </verify>
  <done>Reusable onboarding guard layer is implemented with efficient org-state reuse</done>
</task>
