# Phase 37.2 — Research: Journey Execution Visual Polish (Refactor-Only)

**Date:** 2026-04-08  
**Status:** Complete (synthesis for planning)

## Objective

Answer: *What must execution implementers know to polish the Journey Execution screen without changing behavior or data shapes?*

## Phase scope (from roadmap + product brief)

- **In scope:** Layout density, card segmentation, visual hierarchy (center > right > left), spacing/alignment, elevation and borders, typography rhythm, hover/focus/expand feedback, button tiers, scanability of chapter → standard → OE → status.
- **Out of scope:** New APIs, VM/interface changes (unless purely presentational aliases in templates), routing, store logic changes, redesign from blank slate.

## Prior art in repo

- **Shell:** `src/app/features/journey/pages/execution-screen.component.{ts,html,scss}` — 3-column grid, back action, error/loading states.
- **Panels (execution path — primary edit targets):**
  - `execution-chapter-panel/` — chapter list, search, sort; markup uses **inline BEM** (`.chapter-item`, etc.), not the standalone `chapter-item/` component.
  - `execution-standards-panel/` — hero + standards; markup uses **inline** `.standard-card` / `.oe-item` patterns, not `standards-panel/` / `standard-card/` / `oe-table/` packages.
  - `execution-action-panel/` + `progress-card/` — right column.
- **Legacy / other journey components:** `chapter-navigation/`, `chapter-item/`, `standards-panel/`, `standard-card/`, `oe-table/`, `oe-row/` may exist for older screens — **do not edit unless confirmed imported by `ExecutionScreenComponent`** (currently they are **not**).
- **VM helpers:** `execution-oe-vm.util.ts` — do not change scoring rules; UI labels only if purely cosmetic and already driven by VM.

## Design constraints (non-negotiable)

- `DESIGN_RULES.md` — tokens from `src/styles/tokens/*` and `design-tokens.scss`; 4px spacing scale; semantic colors.
- **No inline styles** in templates; **no raw hex/px** in SCSS unless adding approved tokens in token files.
- **OnPush** + `trackBy` on `*ngFor` where lists exist; no new subscription patterns in presentational components.

## Hierarchy strategy (UX)

| Priority | Column | Treatment |
|----------|--------|-----------|
| Primary | Center | Largest typography for compliance hero; strongest card surface/contrast for standard blocks; OE rows as scannable list items with clear status affordance |
| Secondary | Right | Distinct sub-cards for OE details, progress, primary actions, quick actions; primary CTA visually dominant |
| Tertiary | Left | Slightly muted surface; active chapter clearly selected; risk + progress readable at a glance |

## Elevation & depth (token-led)

- Prefer existing `--shadow-*` and `--color-border-subtle` / `--color-bg-surface-alt` for layering.
- If “glass” depth is insufficient, add **semantic aliases** in `theme.tokens.css` + SCSS map (e.g. execution panel inset header) rather than one-off hex.

## Accessibility

- Preserve or strengthen `:focus-visible` on interactive rows, cards, and buttons; `aria-expanded` on collapsible standards; table/list labels unchanged unless fixing gaps.

## Verification baseline

- Phase 37.1 UAT (`37.1-UAT.md`) — **T7 PARTIAL** (“premium glass” / subjective parity). Phase 37.2 explicitly targets structured layering and hierarchy to close residual polish gaps.

## Risks

- **Component duplication:** Legacy journey components are easy to confuse with execution; **`ExecutionScreenComponent` imports only** `ExecutionChapterPanelComponent`, `ExecutionStandardsPanelComponent`, `ExecutionActionPanelComponent` — polish work belongs in those folders plus `execution-screen` and `progress-card`.
- **Token creep:** batch new aliases in token files; document in plan summaries.
