# Sprint M2.3 — Requirement & Capability Infrastructure Model Implementation Report

Date: 2026-07-05
Scope: Replacing implementation-specific infrastructure declarations with a provider-agnostic
Requirement (what a service needs) / Capability (what an environment provides) model, a
capability registry, a matching engine, deployment-planner integration, environment capability
declaration, publishing integration (compile without resolving), runtime integration (the shared
provisioning pipeline consumes requirements and the planner's matching results), validation and
diagnostics, and regression tests. Kubernetes deployment, cloud-specific provisioners, admission
policies, infrastructure templates, bootstrap redesign, operator UI changes, and multi-cluster
orchestration are explicitly out of scope and were not touched.

## 1. Executive Summary

M2.3 introduces a first-class Requirement/Capability model alongside the infrastructure
declarations M2.1 and M2.2 already established. A `Requirement` is a provider-agnostic statement
of intent a service authors ("I need a SQL database ≥2019", "I need a message broker") — it is
data on the `InfrastructureSpecification`, compiled unchanged into the `InfrastructureContract` by
Publishing, never resolved there. A `Capability` is a provider-specific thing a deployment
environment can supply (SQL Server, PostgreSQL, RabbitMQ, Azure Service Bus, …), catalogued in a
single embedded registry the same way infrastructure specifications and, before that, deployment
manifests already are. Resolution — "can this environment's declared capabilities satisfy this
service's declared requirements" — happens once, at deployment time, in a pure, deterministic
`RequirementCapabilityMatcher`, and its verdict is what the shared `DeploymentPlanner` now uses to
decide `CanDeploy`, alongside the pre-existing `RuntimeCapabilities` boolean checks (kept,
unchanged, for backward compatibility — see §9).

Every service in the platform's specification catalog (`infrastructure-specifications.json`) now
declares real requirements — a database, a certificate, a message broker, an external AI provider,
health monitoring, as applicable — instead of relying solely on the closed boolean set
(`FeatureContract`/`RuntimeCapabilities`) that M2.3 was commissioned specifically to stop
repeating. The open-taxonomy design (`Requirement.Category` is a string, not an enum) means a new
requirement category is new catalog data, never a breaking model change.

The one shared seam both DRV and Runtime Agent execute — `DependencyInfrastructureProvisioner`,
the pipeline stage introduced before this sprint and reused unmodified in spirit through M2.1/M2.2
— is where requirement-capability matching reaches both consumers with zero changes to either
consumer's own source. Neither DRV nor Runtime Agent evaluates a `Requirement` itself; the stage
calls `DeploymentPlanner.Evaluate`, which calls `RequirementCapabilityMatcher.Evaluate`, and fails
the stage if the result says deployment cannot proceed. Because neither caller populates a new
`AvailableCapabilities` list yet, a `LegacyCapabilityBridge` derives an equivalent capability list
from the existing `RuntimeCapabilities` booleans automatically, so every existing deployment path
gets requirement matching for free, without a single line of DRV or Runtime Agent source changing.

As with M2.1 and M2.2, this report must disclose a hard constraint up front: **the sandbox this
work was performed in has no .NET SDK, and every attempt to install one failed** (`curl
https://dot.net/...` → HTTP 403 blocked-by-allowlist; `sudo apt-get install dotnet-sdk` → sudo
disabled, "no new privileges" flag set). No build and no test run has been possible for any of the
three M2.x sprints. Every claim of correctness in this report is the product of careful manual
tracing of the exact code paths involved, not a green test run. This is the single most important
fact for whoever picks this branch up next: **run `dotnet build` and `dotnet test` across the
whole solution in an environment with the SDK available before merging**, exactly as recommended
at the end of M2.1 and M2.2.

## 3. Domain Model

```
Requirement                              Capability
────────────                              ──────────
Id: string                                Id: string
Category: string  ───────satisfies───▶    Category: string
Mandatory: bool                           SatisfiesCategories: string[]
VersionConstraint: string?                Version: string
Description: string                       Aliases: string[]
ValidationRules: string[]                 ProviderMapping: string?
Compatibility                             DependsOnCapabilityIds: string[]
  └ AcceptedCategories: string[]          Description: string

Authored on InfrastructureSpecification   Catalogued in CapabilityRegistry
(one per service, data, never resolved    (one registry, platform-wide,
 by the author or by Publishing)           validated at load: no duplicate
                                            ids, no circular dependencies)

                    RequirementCapabilityMatcher.Evaluate(requirements, availableCapabilities)
                                            │
                                            ▼
                              RequirementMatchResult (per requirement)
                                Status: Satisfied | Missing | IncompatibleVersion
                                MatchedCapability: Capability?
                                Message: string (remediation-aware)
                                            │
                                            ▼
                              RequirementMatchReport
                                Results, CanDeploy, Blockers, Warnings
                                            │
                                            ▼
                              DeploymentPlanner.Evaluate(bundle, runtimeCapabilities,
                                                          requirements, availableCapabilities)
                                folds RequirementMatchReport.Blockers/Warnings into the
                                pre-existing legacy-boolean blockers/warnings
                                            │
                                            ▼
                              DeploymentPlanEvaluation.CanDeploy
                                            │
                                            ▼
                              DependencyInfrastructureProvisioner (shared pipeline stage,
                                executed identically by DRV and Runtime Agent) fails the
                                stage when CanDeploy is false — it never re-implements
                                the match itself.
```

Responsibility boundaries, restated as the sprint's "who does what, when":

- **Service author** (via `infrastructure-specifications.json`): declares `Requirements` —
  intent only, no environment knowledge.
- **`InfrastructureSpecificationValidator`**: rejects unknown categories, duplicate ids, and
  conflicting mandatory version constraints before a specification can even be compiled (D9).
- **Publishing** (`InfrastructureSpecificationCompiler`): copies `Requirements` from the
  specification into the contract unchanged. Never touches `CapabilityRegistry`, never resolves
  anything (D7).
- **Environment operator** (via `EnvironmentCapabilityProfile`): declares what a target
  environment provides, as data, never by probing a live host (D6).
- **`RequirementCapabilityMatcher`**: the one place resolution happens — pure, deterministic,
  replayable (D4).
- **`DeploymentPlanner`**: the one place a deployment decision is made from that resolution,
  alongside the legacy boolean checks it has always made (D5).
- **`DependencyInfrastructureProvisioner`**: the one shared pipeline stage that enforces the
  decision for both DRV and Runtime Agent (D8). Provisioners downstream in the pipeline
  (`DatabaseInfrastructureProvisioner`, `CertificateInfrastructureProvisioner`, etc.) are
  untouched — they still provision what the domain contracts already told them to, exactly as
  before this sprint.

## 4. Matching Flow

1. A service's `InfrastructureSpecification` declares zero or more `Requirement`s (e.g.
   identity-service: `primary-database` [sql-database, mandatory, `>=2019.0`],
   `signing-certificate` [tls-certificates, mandatory], `health-monitoring` [health-monitoring,
   mandatory]).
2. `InfrastructureSpecificationValidator.Validate` calls `RequirementValidator.Validate` and folds
   any errors into the specification's single error list — a specification with an unknown
   requirement category, a duplicate requirement id, or two mandatory requirements in the same
   category demanding incompatible exact versions never compiles at all.
3. `InfrastructureSpecificationCompiler.Compile` copies the (already-validated) requirements
   verbatim into the `InfrastructureContract.Requirements` field. This happens at publish time,
   with no knowledge of any target environment.
4. At deployment time, the target environment's `EnvironmentCapabilityProfile` is resolved to a
   concrete `IReadOnlyList<Capability>` (or, for any caller not yet updated to pass one
   explicitly, `LegacyCapabilityBridge.FromRuntimeCapabilities` derives an equivalent list from
   the legacy booleans already present on every deployment context).
5. `RequirementCapabilityMatcher.Evaluate` matches each requirement against the available
   capabilities: it collects every capability whose `Category` or `SatisfiesCategories` matches
   the requirement's `Category` (or any of its `Compatibility.AcceptedCategories`), then checks
   `VersionConstraint.IsSatisfiedBy` against each candidate's `Version`. The first candidate that
   satisfies the version constraint wins; if none exist, the requirement is `Missing` (no
   candidate category at all) or `IncompatibleVersion` (a candidate category exists, but no
   version satisfies), and the message includes a suggested remediation — the id of a registered
   capability that would satisfy the category, or an upgrade suggestion for the closest match.
6. `DeploymentPlanner.Evaluate` folds the resulting `RequirementMatchReport.Blockers` (from
   `Missing`/`IncompatibleVersion` mandatory requirements) and `.Warnings` (from optional ones)
   into the same `blockers`/`warnings` lists the pre-existing legacy boolean checks already
   populate, and returns a single `DeploymentPlanEvaluation.CanDeploy` verdict — the caller never
   sees two separate pass/fail signals to reconcile.
7. `DependencyInfrastructureProvisioner.ProvisionAsync` — the one pipeline stage both DRV and
   Runtime Agent execute — calls this planner and fails the stage on `CanDeploy == false`.
   Provisioning downstream stages never run their own requirement check; they trust this one
   verdict, exactly as the sprint's Engineering Principles require.

## 6. Validation & Diagnostics

- **`RequirementValidator.Validate`** (D9) runs during `InfrastructureSpecificationValidator.Validate`
  and rejects, in one combined error list: empty ids/categories, categories no registered
  capability could ever satisfy (checked against `CapabilityRegistry.IsKnownCategory`, including a
  requirement's `AcceptedCategories`), duplicate requirement ids within one service, and two
  mandatory requirements in the same category demanding different exact version constraints (a
  deterministic conflict no single capability instance could ever resolve).
- **`CapabilityRegistry.LoadAndValidate`** validates the registry itself at first access: no
  duplicate capability ids, no circular `DependsOnCapabilityIds` graph (via
  `DetectCircularDependencies`, a three-color DFS also exposed publicly so a caller can validate a
  candidate capability set — e.g. an environment profile — before trusting it).
- **`RequirementCapabilityMatcher`** produces a message for every non-`Satisfied` result with
  targeted remediation: for `Missing`, the ids of registered capabilities that would satisfy the
  category (or an explicit "no registered capability satisfies this category at all — check for a
  typo" when none exist); for `IncompatibleVersion`, the specific capability found, its actual
  version, and a suggestion to either upgrade it or relax the requirement's constraint.
- **`EnvironmentCapabilityProfileLoader.ResolveCapabilities`** throws immediately, with the
  offending ids named, if a profile references a capability id the registry does not know — a
  fixture referencing "kubernetes-service" (a real, if unprojected, registry entry) resolves fine;
  a typo would fail loudly at resolution time, not silently produce an empty capability.
- **Diagnostics surfaced to the pipeline**: `DependencyInfrastructureProvisioner` includes every
  `Satisfied` requirement's matcher message in the stage's success output (so a passing deployment
  still records *why* it passed, not just that it did), and every mandatory `Missing`/
  `IncompatibleVersion` message becomes a stage failure error, indistinguishable in shape from the
  pre-existing legacy-boolean failure messages the pipeline has always produced.

## 8. Future Compatibility

- **Kubernetes**: the `kubernetes-service` capability entry (category `network-connectivity`,
  `satisfiesCategories: ["reverse-proxy"]`) and the `kubernetes-cluster` environment profile are
  both declared today specifically so the matching engine can be exercised against a
  cluster-shaped capability set without a real Kubernetes projection existing — no Deployment,
  Service, or Ingress object is generated anywhere in this sprint. When a future sprint implements
  a real Kubernetes provisioner, it becomes a new capability provider registered against the same
  categories every other capability already satisfies; no change to `Requirement`,
  `RequirementCapabilityMatcher`, or any service's declared requirements is anticipated.
- **Docker Swarm**: not modeled explicitly, but structurally identical to the Docker Compose case
  this sprint already supports — a Swarm environment profile would declare `docker-network` plus
  whichever concrete database/broker/certificate capabilities it actually runs; no new requirement
  categories would be needed.
- **Azure Container Apps / AWS ECS**: both are, from this model's perspective, just another
  environment profile with a different capability mix (e.g. ACA's built-in ingress could register
  as a new capability satisfying `reverse-proxy`; ECS's Application Load Balancer likewise). The
  open-taxonomy category design means neither platform requires a new `Requirement.Category` to be
  invented — only new `Capability` entries in the registry.
- **Air-gapped**: already modeled today (§5, §6) — the `air-gapped` environment profile excludes
  every `azure-*` capability, so any service whose requirements can only be satisfied by an Azure
  capability (today: none are mandatory on that path — the `ai` service's `external-ai-provider`
  requirement is non-mandatory specifically to keep it deployable air-gapped) surfaces a warning,
  not a blocker, when deployed against this profile.
- **Hybrid** (mixed self-hosted and managed capabilities within one environment): already
  representable — an environment profile's `capabilityIds` list is just data; nothing prevents a
  profile from declaring `sqlserver` (self-hosted) alongside `azure-key-vault` (managed) in the
  same list, and the matcher does not care which capability satisfies which requirement beyond
  category and version.

## 9. Technical Debt

- **Two parallel deployment-blocking mechanisms coexist by design, not yet unified.** The legacy
  `RuntimeCapabilities` boolean checks in `DeploymentPlanner.Evaluate` (SQL Server, RabbitMQ,
  Service Bus, certificates, Nginx) are kept, unchanged, alongside the new requirement-capability
  matching, exactly as the sprint brief specifies ("Instead of checking infrastructure flags
  directly, it should evaluate: Requirements ↓ Capabilities ↓ Deployment Decision" — read here as
  *in addition to*, given the brief's own Out-of-Scope list excludes a bootstrap/runtime
  provisioning redesign that a full replacement would require). A future sprint should retire the
  boolean checks once every platform service's specification has a requirement covering
  everything a boolean check covers today, and once every real deployment path populates
  `AvailableCapabilities` directly rather than relying on the bridge below.
- **`LegacyCapabilityBridge` is a compatibility shim with two open, intentionally-documented
  gaps.** `RuntimeCapabilities.Redis` has no corresponding entry in `capability-registry.json` and
  is therefore never bridged — deliberately left this way because no `FeatureContract` flag or
  service specification requires Redis today, so adding a capability entry with nothing to satisfy
  would be speculative catalog data. `RuntimeCapabilities.SignalR` is likewise not bridged — it is
  a transport concern with no corresponding `Requirement` category in this sprint's taxonomy, not
  an infrastructure requirement a service declares. Separately, the bridge treats HTTP health
  probing (`http-health-probe`) and Docker network connectivity (`docker-network`) as always
  present whenever `RuntimeCapabilities.Docker` is true, since neither has ever had a dedicated
  legacy boolean of its own — every service's `HealthContract` has always assumed a probe exists
  as a built-in platform-engine capability, not an environment-declared one. This is a reasonable
  reading of "backward compatible," but it is a judgment call, not something the brief specified
  explicitly, and should be revisited once a real environment profile (not the bridge) is the
  normal path.
- **`DependencyInfrastructureProvisioner` now performs real work for services it used to skip
  entirely.** Before this sprint, the stage returned `Skipped` immediately for any service with
  zero declared *service* dependencies, without ever evaluating the legacy boolean checks embedded
  in `DeploymentPlanner` for that service via this stage. Because essentially every platform
  service now declares at least one `Requirement` (most commonly `health-monitoring`), this fast
  skip path effectively no longer triggers for contracts compiled by the specification-driven
  compiler — the stage now genuinely evaluates matching for those services, which is the correct,
  brief-mandated behavior ("Provisioning must execute only after successful matching"), but it
  does mean a previously-silent gap in a real environment's declared capabilities could newly
  surface as a deployment blocker where it previously did not. This is treated as a bug fix, not a
  regression, but must be flagged plainly to whoever ships this: **verify every real
  production/demo/air-gapped environment's actual `RuntimeCapabilities` (or, ideally, a real
  `AvailableCapabilities` list) is complete before this branch reaches any environment**, since a
  gap that was previously invisible (silently skipped) is now enforced.
- **No true Kubernetes, Swarm, ACA, or ECS provisioner exists** — every forward-compatibility claim
  in §8 is structural (the model does not need to change), not functional (nothing was
  implemented). The `kubernetes-service` capability and `kubernetes-cluster` profile are fixtures
  for exercising the matcher, explicitly documented as such in both the registry JSON and the
  profile JSON.
- **No admission/policy engine** decides *which* environment a service is allowed to deploy to
  based on its requirements — that is explicitly M2.4's mandate, not this sprint's. Today, a
  human or an external orchestrator chooses the environment profile to evaluate against; the
  matcher only answers "would this succeed," not "should this be allowed."
- **Secrets Provider, Metrics, Logging, and Network Connectivity requirement categories have
  registered capabilities but zero services that declare them.** This is intentional — the
  registry was populated ahead of demand so those categories are ready the moment a service needs
  them — but it means those code paths are untested against real specification data, only against
  the registry and matcher's own unit tests.

## 10. Readiness Assessment for M2.4 — Deployment Planning & Admission Engine

**What is ready:** the domain model this milestone needed to exist for M2.4 to build on is
complete and, by manual trace, sound — `Requirement`, `Capability`, the registry, the matcher, and
the planner integration all behave as pure, deterministic functions of their inputs, which is
exactly the property an admission engine needs in order to make repeatable, auditable
allow/deny decisions rather than live-probing a target environment. The environment-profile
declaration mechanism (D6) gives M2.4 a natural place to hang admission policy: a policy could be
expressed as "this service's requirements must resolve against this class of environment profile"
without needing any new plumbing between the specification, the contract, and the profile.

**What is a genuine blocker, not just a caveat:** the complete absence of a real build or test run
across three consecutive sprints. This report's regression section is a careful manual trace, and
I have caught and fixed two real, would-have-shipped-broken issues purely by tracing code by hand
(the golden-equivalence test's now-invalid full-hash comparison, and the `params string[]` compile
error from passing a `List<string>` directly to `InfrastructureStageResult.Ready`) — which is
exactly the kind of mistake a compiler catches in seconds and a human tracing code by hand can
miss. M2.4 should not begin until this branch has been built and tested in a real .NET environment
and any compiler errors this trace missed are fixed.

**Recommended before M2.4 starts:**
1. Run `dotnet build` and `dotnet test` across the whole solution. Fix anything this manual trace
   missed.
2. Populate `AvailableCapabilities` directly from each real environment's actual declared profile
   in DRV and Runtime Agent's own call sites, rather than continuing to rely on
   `LegacyCapabilityBridge` as the default path — the bridge exists for zero-touch compatibility
   during this transition, not as the intended long-term mechanism.
3. Decide the two open technical-debt items explicitly rather than leaving them implicit: whether
   to retire the legacy `RuntimeCapabilities` boolean checks now that every service has real
   requirements, and whether to add a `redis` capability-registry entry (only meaningful once a
   service or `FeatureContract` flag actually needs one).
4. Audit every real deployment environment's actual capabilities against the requirements now
   enforced by `DependencyInfrastructureProvisioner` for services that previously skipped this
   stage entirely (see §9) — this is the one place this sprint's correct behavior change could
   surface a previously-latent gap as a new deployment failure.

With those four items addressed, the model this sprint introduces is a reasonable foundation for
M2.4's admission engine: the matching decision is already centralized, already pure, and already
produces a structured, machine-readable verdict (`RequirementMatchReport`) rather than a bare
boolean — exactly the shape an admission policy needs to reason about *why* a deployment would be
denied, not just that it would be.
