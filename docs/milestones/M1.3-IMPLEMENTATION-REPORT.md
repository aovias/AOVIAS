## 1. Executive Summary

Sprint M1.3 transforms the Publishing Engine into a **contract-driven deployment compiler**. All deployable services now declare ports, health probes, dependencies, release-library categories, and solution membership in `deployment.metadata.json`. The publishing pipeline reads this metadata at discovery time and derives manifests, health definitions, dependency contracts, compose files, and solution graphs from it.

**Removed from publishing code:**
- Hardcoded dependency `switch` in `DeployableProjectNaming`
- Hardcoded startup-order `switch`
- Hardcoded release-library category `switch`
- `DemoBundleServiceCatalog` (8-service hardcoded demo list)
- Discovery-driven compose ports/health (replaced by manifest + health contract)
- Empty `manifest.json` dependencies array
- Hardcoded outbox-worker dependency override in `ServiceContractRegistry`

**Preserved:** M1.2 deterministic fingerprints, build identity, staging integrity, and Docker image identity semantics.

**Out of scope (unchanged):** Release library redesign (M1.4), environment-neutral compose (M1.5), infrastructure contract completion (M1.6), Runtime Agent, DRV execution, VPS bootstrap.

## 4. Publishing Dependency Graph

Deployment ordering is generated by `PublishingDependencyGraphBuilder`:

1. Each service's `deployment.metadata.json` declares `dependencies[]`.
2. `BuildGraph()` constructs a directed graph (service → required service dependencies).
3. `TopologicalSort()` produces deterministic startup order (alphabetical tie-breaking).
4. `GetStartupOrder()` assigns rank `(index + 1) × 10` for solution manifest ordering.
5. `ValidateSolutionGraph()` rejects missing targets, duplicate ports, and circular dependencies before solution publish proceeds.

**Evidence (contract-driven):** `SolutionDeployableProjectDiscoverer` no longer calls `DeployableProjectNaming.GetDependencies()` or `GetStartupOrder()`. Ordering for the full platform graph:

```
runtime-agent → gateway → identity-service → organization-service → compliance-service
  ├→ audit-service
  ├→ ai
  ├→ knowledge-base
  ├→ outbox-worker
  └→ portal
```

## 6. Validation Matrix

Publishing fails (Contract Generation stage) when:

| Rule | Condition |
|------|-----------|
| Missing metadata | `deployment.metadata.json` not found at discovery |
| Invalid metadata | Missing `serviceId`, invalid port range, invalid health settings |
| Duplicate dependencies | Same dependency declared twice in metadata |
| Self-dependency | Service depends on itself |
| Manifest drift | Manifest ports/deps/serviceId ≠ metadata |
| Health drift | `health.json` settings ≠ metadata |
| Contract validation | `ContractValidator` failures (ports, secrets, health, volumes) |

Solution discovery fails when:

| Rule | Condition |
|------|-----------|
| Duplicate service IDs | Two projects declare same `serviceId` |
| Unknown dependency | Required dependency not in discovered solution set |
| Duplicate ports | Two services share the same `containerPort` |
| Circular dependency | Cycle detected in dependency graph |

## 7. Extensibility Assessment

**Adding a hypothetical new service (e.g. `notification-service`):**

1. Create project with `Program.cs` and `deployment.metadata.json` declaring serviceId, ports, health, dependencies, membership.
2. Add infrastructure template to `ServiceContractRegistry` (still required until M1.6 generalizes templates).
3. Register project path in platform scan roots (if outside `ComplaincePlatform` / `Aovias.Runtime.Agent`).
4. Run publishing — **no Publishing Engine code changes** for ports, deps, health, demo membership, or manifest generation.

**Remaining manual steps:**
- Infrastructure/secret/database templates in `ServiceContractRegistry` (M1.6)
- Scan root registration for projects outside default directories
- Golden package re-baseline after first publish

## Final Engineering Rule — Verified

The Publishing Engine now behaves as a **generic deployment compiler** for all operational concerns controlled by `deployment.metadata.json`: ports, health, dependencies, startup order, and solution membership. Platform growth for those concerns occurs through new metadata files, not publishing code changes. Infrastructure templates in `Aovias.Deployment.Contracts` remain the next consolidation target (M1.6).
