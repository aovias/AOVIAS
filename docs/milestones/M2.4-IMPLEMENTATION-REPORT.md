# Sprint M2.4 — Deployment Planning & Admission Engine Implementation Report

Date: 2026-07-05
Scope: Separating deployment decision-making from execution via a new Admission Engine and
Deployment Planner, and a new immutable Deployment Plan document Runtime Agent now produces and
validates before provisioning. Kubernetes scheduling, a policy engine, multi-cluster
orchestration, bootstrap redesign, runtime provisioning redesign, and operator UI redesign are
explicitly out of scope and were not touched.

## 1. Executive Summary

Before this sprint, `ReleaseDeploymentProvider.EnsureRuntimeFoldersAsync` both decided whether a
deployment could proceed (via the M2.3 `Planning.DeploymentPlanner.Evaluate` call — legacy
boolean checks plus requirement/capability matching) and, in the same breath, prepared execution
(directory creation, the M2.3 infrastructure provisioning pipeline). There was no document
recording *how* the deployment would proceed — no phase list, no rollback checkpoints, no
certification gates — only a pass/fail verdict and whatever happened next in the hard-coded
method body.

M2.4 introduces two new decision-making layers, in front of everything Runtime Agent already
does, and a new document between them:

An **Admission Engine** (`IDeploymentAdmissionEngine` / `DeploymentAdmissionEngine`) is now the
single place a deployment is approved or rejected. It evaluates eight categories in a fixed,
fail-fast order — Package Integrity, Schema Compatibility, Runtime Compatibility, Requirement
Matching, Capability Matching, Infrastructure Readiness, Environment Validation — and produces a
structured `AdmissionResult` with no partial-approval state. Every rejection carries one or more
`AdmissionDiagnostic` records: category, reason, affected service, affected capability,
remediation, severity, and a correlation id — never a generic error string.

A **Deployment Planner** (`IDeploymentPlanner` / `DeploymentPlanBuilder`) only runs for an
Approved admission result, and only decides *how* a deployment should occur, never whether. It
produces an immutable `DeploymentPlan`: metadata, environment, the service graph, infrastructure
requirements and their match report, deterministic startup ordering, the fixed eight-phase
execution sequence (Preflight → Infrastructure → Upload → Configuration → Deployment → Health →
Certification → Completion) populated with deterministic tasks, health gates, rollback
checkpoints, certification gates, and a recovery strategy.

A **Deployment Plan Validator** (`DeploymentPlanValidator`) checks the plan itself — circular
task dependencies, duplicate or missing phases, missing checkpoints, invalid service ordering,
orphaned tasks, unreachable phases — before Runtime Agent proceeds to the (unchanged)
infrastructure provisioning pipeline. Runtime Agent's `EnsureRuntimeFoldersAsync` now routes
every deployment through Admission, then Planning, then plan validation, and only then continues
to the existing, unmodified provisioning pipeline — replacing the single M2.3
`DeploymentPlanner.Evaluate` call that used to make this decision on its own.

As with every M2.x report before this one, the sandbox this work was performed in has **no .NET
SDK, and every attempt to install one failed** (`curl https://dot.net/...` → HTTP 403
blocked-by-allowlist; `sudo apt-get install dotnet-sdk` → sudo disabled). No build and no test run
has been possible. Every claim of correctness here is a manual trace, not a green test run — see
§7 and §10 for what this means for merge readiness.

## 3. Admission Architecture

```
                         AdmissionRequest (facts only — no I/O inside the engine)
                                    │
                                    ▼
                    ┌───────────────────────────────┐
                    │   DeploymentAdmissionEngine   │
                    │   (IDeploymentAdmissionEngine)│
                    └───────────────────────────────┘
                                    │
        ┌──────────────┬───────────┼────────────┬─────────────────┬────────────────────┐
        ▼              ▼           ▼            ▼                 ▼                    ▼
 Package Integrity  Schema      Runtime    Requirement /   Infrastructure      Environment
 (pre-verified by   Compat.    Compat.     Capability      Readiness           Validation
  the M2.2 reader)  (M2.2      (Version-   Matching        (from the existing  (registration +
                     constants) Constraint  (M2.3 matcher,  provisioning        capability
                     reused)    grammar)    split into two  pipeline's own      profile, M2.3 D6)
                                             stages by       readiness report)
                                             match status)
        │              │           │            │                 │                    │
        └──────────────┴───────────┴────────────┴─────────────────┴────────────────────┘
                                    │  (stops at first Blocking diagnostic)
                                    ▼
                         AdmissionResult { Decision, Diagnostics, EvaluatedCategories }
                                    │
                         Approved ──┴── Rejected (no partial approval)
                                    │
                                    ▼ (only if Approved)
                          IDeploymentPlanner.CreatePlan
```

**Validation stages.** Each stage is a pure function over pre-gathered facts on `AdmissionRequest`:
Package Integrity checks a caller-supplied `Verified` flag (the checksum work already happened
inside `DeploymentPackageContractReader` — Admission does not re-hash anything). Schema
Compatibility confirms the in-memory contract is genuinely at `ContractSchemaVersions.Current`
and that its declared `MaximumSupportedSchemaVersion` is one this runtime recognizes — a
defense-in-depth re-check, since a contract reaching Admission should always already be at the
current schema (the reader guarantees this), but Admission does not simply trust that. Runtime
Compatibility reuses M2.3's `VersionConstraint` grammar against an optional
`MinimumRuntimeAgentVersion` (a forward-compatible hook — no contract field carries this today,
see §9). Requirement Matching and Capability Matching share one call to
`RequirementCapabilityMatcher.Evaluate` (M2.3 D4) and split its two failure modes
(`Missing` → Requirement Matching, `IncompatibleVersion` → Capability Matching) into the brief's
two named categories. Infrastructure Readiness and Environment Validation are the last two gates
before Approval.

**Decision model.** `AdmissionResult.Decision` is `Approved` only when zero `Blocking` diagnostics
were produced across every category reached. There is no partial-approval state: a single
mandatory-requirement failure rejects the whole request, exactly as a missing legacy boolean
capability always has. Evaluation stops at the first category producing a blocking diagnostic
(`EvaluatedCategories` records exactly how far it got) — a design decision beyond what the brief
strictly mandates, made so a rejection's diagnostics are always about the one real cause, not a
mixture of a root failure and whatever unrelated noise a later, never-reached category might
otherwise have reported.

## 4. Deployment Planner

**Architecture.** `DeploymentPlanBuilder` is the sole `IDeploymentPlanner` implementation. It
requires `DeploymentPlanRequest.Admission.Decision == Approved` as an explicit precondition,
throwing `InvalidOperationException` otherwise — planning cannot run for a rejected request even
if a caller tries to force it, which is what makes "Admission precedes planning" a structural
guarantee rather than a convention.

**Phase generation (D5).** The eight execution phases are fixed platform policy, not a per-plan
choice: every `DeploymentPlan` declares exactly `Preflight, Infrastructure, Upload, Configuration,
Deployment, Health, Certification, Completion`, in that order, with `Order == (int)Name` always.
Each phase is populated with a deterministic task list derived from the bundle/contract's own
data — Preflight always re-states the admission checks that already passed; Infrastructure gets
one task per required certificate, required secret, and declared `Requirement`; Upload is fixed
(extract, stage); Configuration gets one task per required configuration key; Deployment gets a
backup task, one start-task per resolved startup-order entry, and an activate task; Health gets
one task per required health probe; Certification and Completion are fixed.

**Task generation and dependency ordering.** Tasks form one long linear chain end-to-end: every
task depends on the task immediately before it, across phase boundaries (the first task of phase
N+1 depends on the last task of phase N). This is a deliberate simplification — a real
multi-branch dependency DAG was not built — chosen because it trivially guarantees the plan is
free of circular dependencies and orphaned references by construction, while still faithfully
encoding "phases run in this order, and within a phase, tasks run in this order." See §9 for why
this is flagged as technical debt rather than presented as a fully general solution.

**Dependency resolution (D2).** `BuildStartupOrder` mirrors the same approach
`Planning.DeploymentPlanner`'s pre-existing private `TopologicalSort` has used since Sprint
M2.0 — deduplicating declared dependency ids and appending the primary service last. It is not a
true multi-level topological sort (it has never needed to be, since no service today declares a
transitive dependency chain deeper than one level) — see §9.

**Rollback planning (D7).** `BuildRollbackPoints` always identifies "before upload," "before
infrastructure changes," and "before service replacement," adds "before database migration" only
when `bundle.Database.Required` is true (a service with no database has nothing to migrate), and
always adds "before certification." Planning only identifies these points — no rollback executes
as part of building a plan.

## 5. Deployment Plan Model

| Section | Owner (who populates it) | Lifecycle |
|---|---|---|
| `Metadata` | `DeploymentPlanBuilder`, from the bundle/contract and the admission result's correlation id | Deterministic `PlanId` (`{ServiceId}:{ServiceVersion}:{ContractContentHash}`), never a random guid — the same approved deployment always yields the same plan identity. `GeneratedUtc` is supplied by the caller, not read from the clock inside the planner. |
| `Environment` | Caller-supplied `EnvironmentId`/`CapabilityProfileId` on `DeploymentPlanRequest` | Restates which environment (and, if declared, which M2.3 capability profile) this plan was built against. |
| `Services` | `DeploymentPlanBuilder`, from `bundle.Manifest` + `bundle.Dependency.Dependencies` | The primary service plus every declared dependency; validated against `Dependencies` (startup order) by `DeploymentPlanValidator`. |
| `Infrastructure` | `DeploymentPlanBuilder`, from the contract's `Requirements` and the bundle's filesystem/secret/certificate contracts, plus the `RequirementMatchReport` already evaluated | Self-describing: a caller inspecting a plan never needs to re-run matching to know why it was approved. |
| `Dependencies` | `DeploymentPlanBuilder` | Deterministic startup order (see §4). |
| `ExecutionPhases` | `DeploymentPlanBuilder` | The fixed eight-phase, linear-task-chain sequence (§4). Immutable once the plan is constructed — Runtime provisioners consume it, they do not append to or reorder it. |
| `HealthGates` | `DeploymentPlanBuilder`, from `bundle.Health` | One gate per required probe actually declared. |
| `RollbackPoints` | `DeploymentPlanBuilder` (§4/D7) | Planning-time identification only; no execution semantics attached in this sprint. |
| `CertificationGates` | `DeploymentPlanBuilder`, fixed set mirroring `VerifyDeploymentAcceptanceAsync`'s existing checks | Restates existing runtime acceptance checks as planned data. |
| `Recovery` | `DeploymentPlanBuilder` | `RollbackToPrevious` is the only strategy this platform's execution model supports today; `TriggersOnPhaseFailure` is derived from `RollbackPoints`. |
| `Diagnostics` | `DeploymentPlanBuilder`, last step of `CreatePlan` | Carries forward admission warnings (by message only) and the plan's own content hash (§4/D10), computed after every other section is final. |

**Immutability.** Every property on every plan type is `init`-only and every collection is a
read-only list — a `DeploymentPlan`, once returned from `CreatePlan`, cannot be mutated by any
caller, matching Final Engineering Rule 4 ("Deployment Plans are immutable after approval")
structurally, not just by convention.

(traced by hand, not run):

**Requirement failure** (mandatory `sql-database` requirement, no capability at all):
```

         environment. Suggested remediation: add capability sqlserver or postgresql to this
         environment's declared profile."

AffectedCapability: "sql-database"
Remediation: "add capability sqlserver or postgresql to this environment's declared profile."
Severity: Blocking
CorrelationId: "REL-2026-0705-001"
```

**Capability failure** (a `sql-database` capability exists, but at the wrong version):
```
Category: CapabilityMatching
Reason: "Requirement 'primary-database' (sql-database) found capability 'sqlserver' at version
         2022.0.0, which does not satisfy constraint '>=2025.0'. Suggested remediation: upgrade
         'sqlserver' or relax the requirement's version constraint."
AffectedService: "identity-service"
AffectedCapability: "sql-database"
Remediation: "upgrade 'sqlserver' or relax the requirement's version constraint."
Severity: Blocking
CorrelationId: "REL-2026-0705-001"
```

**Version incompatibility** (Runtime Agent below the package's declared minimum):
```
Category: RuntimeCompatibility
Reason: "Runtime Agent version 1.5.0 is below the package's minimum required version 2.0.0."
AffectedService: "identity-service"
AffectedCapability: null
Remediation: "Upgrade Runtime Agent to at least version 2.0.0 before retrying this deployment."
Severity: Blocking
CorrelationId: "REL-2026-0705-001"
```

**Infrastructure readiness failure** (reusing the existing pipeline's own blocker text):
```
Category: InfrastructureReadiness
Reason: "Runtime does not provide certificate provisioning capability."
AffectedService: "identity-service"
AffectedCapability: null
Remediation: "Resolve the infrastructure provisioning blocker reported by
              InfrastructureProvisioningPipeline, then retry."
Severity: Blocking
CorrelationId: "REL-2026-0705-001"
```

There is no generic "unexpected error" diagnostic anywhere in `DeploymentAdmissionEngine` — every
one of the seven categories has its own, specific `Reason`/`Remediation` text, and every
diagnostic always carries `AffectedService` and `CorrelationId`.

## 7. Regression Results

**No test has been executed.** As in every M2.x report before this one: no .NET SDK is available
in this sandbox, and installing one is blocked at the network and OS-privilege level. The
following is a manual trace of what each new test asserts, not a report of a real test run.

New: `Aovias.DeploymentValidation.Tests/DeploymentAdmissionAndPlanningTests.cs` (D10), covering:

- **Admission success**: every category passes and produces `Approved` with zero blockers, and a
  case where an optional requirement goes unmet, producing a `Warning` diagnostic while still
  approving.
- **Admission failure**, one test per category: Package Integrity, Schema Compatibility (an
  out-of-range `SchemaVersion`), Runtime Compatibility (a version-constraint mismatch),
  Requirement rejection (`Missing`), Capability rejection (`IncompatibleVersion`), Infrastructure
  Readiness (a supplied blocker propagates verbatim), and Environment Validation (unregistered
  environment) — each asserting the correct `AdmissionCategory` and, for the integrity case, that
  evaluation stopped after exactly one category (fail-fast).
- **Determinism**: the same `AdmissionRequest` evaluated twice produces identical decisions,
  diagnostic counts, and evaluated-category lists.
- **Deployment Plan generation**: `DeploymentPlanBuilder.CreatePlan` throws
  `InvalidOperationException` for a rejected admission result; a plan built from an approved
  request always contains exactly the eight canonical phases in canonical order; the
  "before-database-migration" rollback checkpoint appears only when the bundle's database is
  required (identity-service, which requires one); dependency ordering includes every declared
  dependency with the primary service always last (gateway → runtime-agent case).
- **Deterministic planning**: two plans built from the same bundle/contract/capabilities but
  different `CorrelationId`s and `GeneratedUtc` timestamps produce an identical
  `Diagnostics.ContentHash` — proving the hash is a function of deployment content, not of
  incidental request metadata.
- **Plan validation** (D9): a plan produced by the real builder passes validation cleanly; a
  hand-built minimal valid plan also passes (a baseline sanity check independent of the builder);
  and one targeted failure test per rule — missing phase, orphaned task dependency, circular task
  dependency (two tasks depending on each other), missing rollback checkpoints, invalid service
  ordering (an undeclared service in the startup order), and duplicate phase.

## 8. Future Compatibility

- **Policy-based admission**: `AdmissionResult`'s structured `Diagnostics` and
  `EvaluatedCategories` are exactly the shape a policy engine would need to reason about — a
  future policy layer could sit either inside `DeploymentAdmissionEngine` as an additional
  category, or as a caller that inspects an `AdmissionResult` and applies further rules before
  acting on `Approved`. No rework of the existing seven categories is anticipated.
- **Multi-environment deployment**: `DeploymentPlanEnvironment` and
  `EnvironmentRegistrationFacts.CapabilityProfileId` already carry an environment identity through
  both Admission and the Plan; evaluating the same contract against several environment profiles
  today only requires calling both engines once per environment — no model change needed.
- **Kubernetes execution**: as in M2.3, no real projection exists; the `kubernetes-service`
  capability and `kubernetes-cluster` profile remain fixtures. This sprint's `DeploymentPlan`
  model is execution-target-agnostic (phases and tasks describe *what* must happen, not
  container-runtime-specific *how*), so a Kubernetes executor consuming a `DeploymentPlan` is
  architecturally plausible without a plan-model change — but no such executor exists.
- **Blue/Green deployment**: the plan's `Services`/`Dependencies`/`ExecutionPhases` structure
  could represent two parallel service versions today only by producing two separate
  `DeploymentPlan` instances; there is no first-class "plan pair" or traffic-shifting concept yet.
  This would need new plan sections, not just new capability data.
- **Canary deployment**: similarly not modeled — there is no percentage-based or
  gradual-rollout concept anywhere in `DeploymentPlan`. A canary phase would likely need a new
  `DeploymentExecutionPhaseName` value (or a sub-phase concept), which is a real, not-yet-designed
  extension point.
- **Multi-node orchestration**: `DeploymentPlan` is scoped to one service's deployment (mirroring
  the platform's existing one-release-one-service execution model); it has no concept of
  scheduling across multiple runtime nodes. This is the largest remaining architectural gap for
  any of the six items above beyond Kubernetes/policy/multi-environment.

## 9. Technical Debt

- **Startup ordering is deduplication, not a true topological sort**, in both the pre-existing
  M2.0-era `Planning.DeploymentPlanner.TopologicalSort` and this sprint's new
  `DeploymentPlanBuilder.BuildStartupOrder`. Neither has ever needed to resolve a multi-level
  transitive dependency chain because no platform service declares one today. This is a carried-
  forward gap, not one this sprint introduced, but M2.4 doubles the surface area that would need
  fixing if that assumption ever stops holding.
- **Task dependencies are a single linear chain, not a real DAG.** Every task depends only on the
  one immediately before it, even across phase boundaries. This trivially satisfies "no circular
  dependencies" and "no orphaned tasks" by construction, but it does not model genuine
  parallelism (e.g., provisioning a certificate and a secret at the same time, which are
  independent of each other today) — a real execution engine wanting to parallelize within a
  phase would need `DeploymentPlanBuilder` to build a genuine dependency graph instead.
  Recommend: **defer** — no current execution engine exists that could exploit parallelism
  anyway (out of this sprint's scope), so building a richer graph now would be speculative.
- **Two coexisting "planner" concepts.** `Planning.DeploymentPlanner.Evaluate` (M2.3) and the new
  `IDeploymentPlanner`/`DeploymentPlanBuilder` (M2.4) both exist in the same namespace, doing
  related but distinct jobs — the former is still the single source of truth for the shared
  `DependencyInfrastructureProvisioner` pipeline stage both DRV and Runtime Agent execute; the
  latter is the new full plan-document builder, used (so far) only by
  `ReleaseDeploymentProvider.EnsureRuntimeFoldersAsync`. Recommend: **refactor in a future sprint**
  — once `DependencyInfrastructureProvisioner` is updated to consume `DeploymentPlan` output
  directly (a natural next step, but a provisioner-redesign concern this sprint's Out of Scope
  list excludes), the M2.3 `Evaluate` boolean-plus-requirement gate could likely be retired
  entirely in favor of always going through Admission + Planning first.
- **`DeploymentAdmissionEngine`/`DeploymentPlanBuilder` are held as static fields, not
  DI-registered services**, in `ReleaseDeploymentProvider`. This was a deliberate, low-risk choice
  (both are pure and stateless, and adding two more constructor parameters would touch every
  existing DI registration and any future test that constructs this class) but it does mean
  neither is currently swappable via DI for testing or for an alternate implementation.
  Recommend: **refactor** — register both via `IServiceCollection` and inject them once a second
  real caller (e.g., DRV) needs to use them, at which point the DI wiring earns its cost.
- **DRV's existing validation stage pipeline was not unified with the new Admission Engine.** DRV
  (`Aovias.DeploymentValidation`) already has its own independently-evolved sequence of validation
  stages (Package, Contracts, Compatibility, Docker Compose, Bootstrap, Configuration,
  Infrastructure, Runtime, Health, Rollback, Environment Neutral) that overlaps conceptually with
  several Admission categories (Package Integrity, Schema Compatibility, Infrastructure
  Readiness). This sprint deliberately left DRV untouched to keep blast radius contained to
  Runtime Agent (D6's explicit target) and to avoid an implicit "DRV pipeline redesign," which
  the brief's Out of Scope list would treat as adjacent to "runtime provisioning redesign."
  Recommend: **defer**, but flag clearly — a future sprint should decide whether DRV's pipeline
  becomes a caller of `IDeploymentAdmissionEngine` (consolidating the decision logic into one
  place) or remains a deliberately separate, dry-run-only validation surface.
- **`MinimumRuntimeAgentVersion` has no home on any contract today.** Runtime Compatibility's
  check is fully implemented and tested, but `AdmissionRequest.MinimumRuntimeAgentVersion` is
  always `null` in the one real caller (`ReleaseDeploymentProvider`) because no field anywhere in
  `InfrastructureContract` or `ServiceManifest` carries a minimum runtime version today.
  Recommend: **defer** until a real need for per-package minimum runtime versions emerges; the
  hook exists and is tested, but wiring a real value through requires either a contract schema
  addition (a new, out-of-scope-for-this-sprint schema evolution) or a manifest field.
- **Environment registration is always `true` today.** No external environment registry exists;
  `ReleaseDeploymentProvider` sets `Registered = true` unconditionally because the runtime
  evaluating the request is definitionally its own target environment. This is honestly
  documented, not hidden, but it means the Environment Validation category is currently
  exercised only by its `CapabilityProfileId` resolution check, never by a real "is this
  environment registered" decision. Recommend: **defer** to whatever future sprint introduces a
  real environment registry (likely part of the "multi-environment deployment" work in §8).

## 10. Readiness Assessment

**What is ready:** the decision/execution separation this milestone was commissioned to build is
real and structural, not cosmetic. `DeploymentPlanBuilder.CreatePlan` throws if handed anything
but an `Approved` admission result — this is enforced in code, not just documented. Every plan is
immutable and independently re-validated before Runtime Agent proceeds. The Admission Engine's
diagnostics are genuinely structured (category, reason, affected service/capability, remediation,
severity, correlation id) with no generic-error fallback path anywhere in its seven categories.
This gives M2.5 a clean, well-defined interface to build an execution runtime against: a validated
`DeploymentPlan` with phases and tasks already resolved, rather than an ad hoc pass/fail boolean.

**What is a genuine blocker:** the same one every M2.x report has disclosed — zero real build or
test runs across four consecutive sprints. This report's manual trace caught and fixed a real
scoping bug during this very sprint (an initial draft of the `EnsureRuntimeFoldersAsync` edit
referenced a `readiness` report from inside a conditional block it was no longer in scope for,
and called a non-existent helper method) purely through careful re-reading, not compilation. That
class of mistake is exactly what a real compiler catches immediately and a manual trace can miss.
**M2.5 must not begin until this branch has been built and tested in a real .NET environment.**

**Recommended before M2.5 starts:**
1. Run `dotnet build` and `dotnet test` across the whole solution.
2. Decide whether `DependencyInfrastructureProvisioner` (the shared DRV/Runtime Agent pipeline
   stage) should be updated to consume the new `DeploymentPlan`'s `ExecutionPhases`/tasks
   directly, which would let the M2.3 `Planning.DeploymentPlanner.Evaluate` boolean-plus-
   requirement gate be retired rather than continuing to coexist with the new engines.
3. Decide whether DRV should become a second caller of `IDeploymentAdmissionEngine` (see §9).
4. If M2.5's "Infrastructure Provisioning Engine & Execution Runtime" is meant to actually walk
   `DeploymentPlan.ExecutionPhases`/`Tasks` and drive real provisioners from them (rather than the
