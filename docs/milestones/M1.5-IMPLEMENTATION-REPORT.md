## 1. Executive Summary

Before this sprint, the Release Library was exactly what the mission statement warns against: a folder. Two independent, uncoordinated code paths wrote `.aovdeploy` files into it — a static `ReleaseLibraryOrganizer.Organize(root, project, packagePath)` helper used by the per-service pipeline and the solution orchestrator, and a second, separate flat-copy implementation inside `ComplianceServiceManager`'s `PublishingWorkspaceService.AddToReleaseLibraryAsync`. Neither tracked lifecycle, neither recorded metadata beyond a filename, and neither could answer "is this artifact certified," "what's the latest Gateway," or "what would I roll back to" without scanning the filesystem and re-deriving everything from scratch. There was no index, no lifecycle model, no retention policy, and no integrity verification beyond what the DRV package-verification stage already did once at publish time.

This sprint replaces both duplicate implementations with a single authoritative service, `IReleaseLibraryService`, backed by a persisted JSON index (`release-index.json`) rather than directory enumeration. Every artifact now carries a full lifecycle (Building → Published → Verified → Certified → Ready → Deployed → Promoted, with Deprecated/Archived as side branches), a separate promotion ladder (Draft → Verified → Certified → Production Approved → Deprecated), and a metadata record whose every field is sourced from a value the Publishing pipeline had already computed — nothing is recalculated or duplicated. Registration is idempotent for identical content and hard-fails on genuine collisions (same artifact ID with different content, or the same fingerprint claimed by two different services). A query API (D9) gives Runtime Agent, rollback, and future CI/CD consumers a way to ask the library directly instead of walking the filesystem. A conservative, two-phase retention model (archive first, delete only what is already archived and stale) protects deployed, certified, and rollback-candidate artifacts from ever being deleted by policy.

The canonical 13-stage pipeline order was **not** changed — `PublishingPipeline8DTests.CanonicalOrder_ContainsRequiredStages` asserts `DeploymentCertification` is the last stage, and reordering to put library registration after certification would have broken that passing test for no real benefit. Instead, the `ReleaseLibrary` stage now performs D10 pre-flight validation (using the fingerprint and metadata already available at that point), and the actual `RegisterPublishedAsync` / `AdvanceToCertifiedAsync` calls happen inside `RunDeploymentCertificationAsync`, once the final package exists. Both the `SolutionPublishingOrchestrator`'s categorized copy and CSM's ad hoc "add finished package to library" action now delegate to the same service instead of each doing their own file copy — closing the "no duplicate implementations" requirement from D1/D9.

**Sandbox limitation, disclosed as it was in M1.4:** this environment has no .NET SDK installed and network egress to install one is blocked. Every claim about build correctness in this report comes from manual, line-by-line signature tracing — reading every modified constructor, every call site, every interface member, and every DI registration to confirm they agree — not from an actual `dotnet build` or `dotnet test` run. That tracing is documented in §8. If a real build environment is available, running `dotnet build` and `dotnet test` on `Aovias.Publishing.sln` (or at minimum the `Aovias.Publishing.Core` and `Aovias.Publishing.Core.Tests` projects plus `ComplianceServiceManager`) is the natural next step to convert this from "traced correct" to "verified correct."

## 3. Release Library Architecture

**Storage.** The library root is the same directory every existing caller already used as `OutputDirectory`/`releaseLibraryRoot` — no new configuration setting was invented. Under that root, packages are stored by category (`{root}/{ReleaseLibraryCategory}/{serviceId}-{version}.aovdeploy`, category defaulting to `Services`), and a single hidden index directory, `{root}/.release-index/release-index.json`, holds the authoritative record of everything in the library. The package files themselves are still plain `.aovdeploy` archives — the change is that nothing is ever supposed to discover them by listing that directory again.

**Index.** `ReleaseIndexDocument` is the whole library's state: a schema version, a last-updated timestamp, and the flat list of `ReleaseArtifactRecord`s. `ReleaseIndexStore.Load`/`Save` (§6) are the only code that ever touches `release-index.json` directly.

**Metadata.** `ReleaseArtifactRecord` (§5) is the single record type. It is a C# `record`, not a class, specifically so lifecycle transitions can be expressed as `existing with { ... }` — immutable, traceable updates rather than in-place mutation.

**Query model.** `IReleaseLibraryQueries` (implemented by `ReleaseLibraryService`) is the read surface: find by artifact ID, version, service, platform version, fingerprint, or source revision; find latest, latest certified, latest platform bundle, compatible Runtime Agent, or rollback candidate (§9 in the spec, D9 here). Every method takes the release-library root explicitly as its first parameter — there is no implicit "current root" state, because `ReleaseLibraryService` is registered as a singleton and could be queried concurrently against different roots (a solution publish and a CSM ad hoc registration could, in principle, target different library roots at the same time).

**Lifecycle.** See §4.

**Concurrency and durability.** Every mutation (`RegisterPublishedAsync`, every `*Async` transition, `ApplyRetentionAsync`) takes a per-root `SemaphoreSlim` before reading, modifying, and re-saving the index — needed because `SolutionPublishingOrchestrator` publishes services in parallel via `Parallel.ForEachAsync`, and multiple services can be registering into the same library root simultaneously. `ReleaseIndexStore.Save` writes to a temp file and `File.Move(overwrite: true)`s it into place, so a crash mid-write can never leave a half-written, corrupt index on disk.

**Duplicate-implementation elimination.** Two call sites previously wrote into the library independently:
1. `ReleaseLibraryOrganizer.Organize` (used by the per-service pipeline stage indirectly via the solution orchestrator, and directly by the solution orchestrator) — **deleted**, replaced by `RegisterOrganizedCopyAsync(root, project, packagePath, ct)`.
2. CSM's `PublishingWorkspaceService.AddToReleaseLibraryAsync` — its inline `File.Copy` **removed**, replaced by a call through `IPublishingClient.RegisterInReleaseLibraryAsync`, which is a thin facade over a new `RegisterOrganizedCopyAsync(root, packagePath, ct)` overload that derives service identity entirely from the package's own manifest (CSM never had a discovered `DeployableProject` to pass in).

Both call sites now write through the same `ReleaseLibraryService`, the same index, and the same lifecycle rules.

## 4. Artifact Lifecycle

| State | Meaning | Owning subsystem | Reachable from |
|---|---|---|---|
| `Building` | Publishing pipeline is producing the artifact; not yet registered | Publishing (transient, never persisted as the current state of a registered record) | — |
| `Published` | A complete, checksummed package exists and has been registered | Publishing (`RegisterPublishedAsync`) | `Building` |
| `Verified` | Package verification (required files, checksums, contracts) passed | Package verification (`AdvanceToVerifiedAsync`) | `Published` |
| `Certified` | Deployment certification produced a deployment-readiness certificate | Deployment certification (`AdvanceToCertifiedAsync`) | `Published`, `Verified` |
| `Ready` | Passes every Release Library integrity/lifecycle gate; deployable | Release Library itself (`AdvanceToReadyAsync`) | `Published` … `Certified` |
| `Deployed` | A Runtime Agent deployment of this artifact succeeded | Runtime Agent / deployment execution — **API surface only, not called by this sprint's code; out of scope for M1.5** (`MarkDeployedAsync`) | `Published` … `Ready` |
| `Promoted` | Promoted to a higher environment tier | Promotion workflow — **API surface only, out of scope** (`MarkPromotedAsync`) | `Published` … `Deployed` |
| `Deprecated` | Superseded by a newer artifact; retained for rollback/audit only | Whichever subsystem supersedes it (`MarkDeprecatedAsync`) | Any state except `Archived` itself |
| `Archived` | Retained for historical/audit purposes only; excluded from deployable queries | Retention policy (`ArchiveAsync`) | Any state except itself |

Transition rules (`ArtifactLifecycleTransitions`, enforced by `EnsureValidTransition` on every mutating call):
- Forward-only along the canonical order above; **skipping ahead is allowed** (e.g. `Published → Certified` directly, if an intermediate stage is bypassed) but moving backward is always rejected.
- `Deprecated` and `Archived` are reachable as side branches from any in-service state (not just linearly).
- Once in `Deprecated` or `Archived`, no further forward transition is possible — `Archived` is terminal; `Deprecated` can still move to `Archived`.
- Every transition is validated against the record's *current* state read from the index at the moment of the call (inside the per-root semaphore), not a stale in-memory copy, so a bad transition from a concurrent writer is caught rather than silently overwritten.
- Every transition appends an `ArtifactLifecycleTransition(FromState, ToState, TransitionUtc, Owner, Reason?)` to the record's `Transitions` list — a full, queryable audit trail, not just a current-state flag.

**Publishing may only advance artifacts to `Published`.** Confirmed: `RegisterPublishedAsync` is the only method that creates a new record, and it always ends in `WithTransition(ArtifactLifecycleState.Published, "Publishing")`. **Deployment certification advances to `Certified`.** Confirmed: only `AdvanceToCertifiedAsync`, called from `PublishingStageExecutor.RunDeploymentCertificationAsync`, sets that state. **Deployment success advances to `Deployed`** and **promotion advances to `Promoted`** are both implemented as API surface (`MarkDeployedAsync`, `MarkPromotedAsync`) that no in-scope caller invokes yet — correctly, since Runtime Agent deployment execution and promotion workflows are out of scope for M1.5. They exist so M1.6+ work has a contract to call into rather than needing to modify the Release Library again.

The Release Library reads them; it never recomputes a hash, a fingerprint, or a contract version independently.

## 6. Release Index

- **Storage:** `{releaseLibraryRoot}/.release-index/release-index.json`, one document per root, containing every registered artifact.
- **Synchronization:** All reads and writes for a given root go through a per-root `SemaphoreSlim` inside `ReleaseLibraryService`, so concurrent solution-wide publishes (`Parallel.ForEachAsync` in `SolutionPublishingOrchestrator`) can't interleave a read-modify-write cycle. An in-memory `ConcurrentDictionary<string, ReleaseIndexDocument>` cache (`cachedIndexes`) serves read-only queries without re-reading disk on every call, but every mutating path re-reads from disk under the semaphore first, so the cache can never be the source of a stale write.
- **Recovery:** An index file that doesn't exist yet is not an error — a fresh, empty document is returned (a brand-new release library root is a normal, valid state). An index file that exists but fails to parse, is empty, deserializes to null, or contains duplicate artifact IDs **is** an error — `ReleaseIndexStore.Load` throws `InvalidOperationException` rather than silently treating a corrupted library as an empty one. This is the D10 "corrupted index" requirement: fail loudly, never mask.
- **Validation:** Beyond the corruption checks above, every registration re-validates the whole-index invariant that no two artifacts share an ID with different fingerprints and no two artifacts across services share a fingerprint (§below), and every transition re-validates against `ArtifactLifecycleTransitions` before being persisted.

## 7. Artifact Integrity

**Strategy.** `VerifyIntegrityAsync(root, artifactId)` checks, in order: (1) the artifact is actually present in the index — an artifact the index doesn't know about can never be "deployable" by definition; (2) the stored package file still exists on disk; (3) the stored package's current SHA-256 hash still matches the hash recorded at registration time (`PublishingContentHasher.HashFile`, the same utility used at registration — no separate hashing logic); (4) the stored package still passes `IDeployPackageVerifier.VerifyAsync` (the same required-files/checksum/certificate verifier the pipeline already runs at publish time, re-run here against the *stored* copy rather than the just-built one). `VerifyAllIntegrityAsync` runs this over every artifact currently in the index — this is the mechanism by which "corrupt artifacts must never appear deployable" (D5) is enforced continuously, not just at publish time.

**Corruption detection.** Two independent signals: a package-hash mismatch (the stored bytes were modified or the file was silently truncated/replaced after registration) and a failed package verifier run (missing required files, broken checksums, or a missing certificate for an artifact that claims to be certified). Either produces a non-empty `Errors` list and `IsIntact == false`; a missing package file short-circuits immediately with its own explicit error rather than attempting to hash a file that isn't there.

**Duplicate detection (D10, enforced at registration, not as a separate integrity pass):** registering an artifact ID that already exists with a *different* fingerprint is a hard failure — a version must never be silently overwritten with different content; a new version number is required instead. Registering a fingerprint that's already claimed by a *different* service is also a hard failure — a content collision across services is treated as an anomaly worth investigating, not coincidence. Registering the *same* artifact ID with the *same* fingerprint is treated as an idempotent no-op-ish re-registration: storage facts (hash, size, relative path) are refreshed, but lifecycle and promotion state are never regressed.

## 10. Risk Assessment

## 11. Readiness Assessment for Sprint M1.6 — Infrastructure Template Compiler & Deployment Package Finalization

The Release Library is now positioned to be a real dependency for M1.6 rather than a filesystem detail it has to work around:

- **Ready:** The query API (D9) — `FindLatestCertified`, `FindCompatibleRuntimeAgent`, `FindLatestPlatformBundle`, `FindRollbackCandidate` — is exactly the kind of surface an infrastructure/bundle compiler needs to ask "what am I compiling a template for" without touching the filesystem.
- **Ready:** The metadata model already carries `ContractVersion`, `PublishingEngineVersion`, and `DeploymentCompatibility`, which M1.6's infrastructure contract work (`InfrastructureContractBuilder`, noted as not yet wired into packaging per the M1.4 report) can consume directly rather than re-deriving.
- **Needs attention before M1.6 relies on it:** the D8 `PlatformVersion`/`Solution` population gap (§9) should be closed first if M1.6's "deployment package finalization" work is meant to operate at the solution/bundle level — right now `GetSolutionComposition` is correct but will return nothing for any artifact registered without an explicit platform version, which today is every real registration.
- **Needs attention:** actual `dotnet build`/`dotnet test` execution, once a real build environment is available, to convert this sprint's manual signature-tracing into verified fact. This is the single highest-priority follow-up, called out three times in this report for that reason.
- **Not blocking:** rollback execution, promotion workflows, and CI/CD integration remain correctly unimplemented — their API surface exists (`MarkDeployedAsync`, `MarkPromotedAsync`, the rollback-candidate query) without any premature workflow logic, which is exactly the "establish lifecycle support, not workflow" instruction this sprint was given for D6.

Overall: the Release Library is now index-backed, lifecycle-aware, integrity-checked, and duplicate-free, and every acceptance criterion in the sprint brief is met with one disclosed exception (D8's platform-version population) and one disclosed environmental constraint (no compiled build verification). Both are named explicitly rather than left for M1.6 to discover.
