# Sprint M2.5 — Infrastructure Provisioning Engine & Execution Runtime Implementation Report

Date: 2026-07-06
Scope: Turning Runtime Agent into a deterministic execution engine for already-approved,
already-validated Deployment Plans (M2.4). Blue/Green, Canary, multi-node execution, a real
Kubernetes runtime, cloud provider execution, operator UI redesign, and deployment analytics are
explicitly out of scope and were not touched. The Admission Engine, Deployment Planner, Runtime
Contracts, Publishing, and Bootstrap were not redesigned.

## 1. Executive Summary

Before this sprint, an approved, validated `DeploymentPlan` (M2.4) was a document Runtime Agent
produced and logged metadata about — nothing actually walked its `ExecutionPhases`/`Tasks` and
drove work from them. Real provisioning still happened through the pre-existing, independent
`InfrastructureProvisioningPipeline` call and the external `Aovias.Orchestration` step sequence,
neither of which read the plan at all. M2.4's own Readiness Assessment (§10) named this exact gap
as the real architectural work M2.5 needed to do.

M2.5 adds a new **Execution Runtime** (`IDeploymentExecutionRuntime` / `DeploymentExecutionRuntime`)
that is the one and only place a `DeploymentPlan`'s tasks actually run. It walks
`ExecutionPhases` in the exact order the plan declares — never a hardcoded order of its own —
dispatching every `DeploymentTask` to a provisioner resolved by a new
`InfrastructureTaskProvisionerRegistry` (first-match-wins, with a `NoOpTaskProvisioner` fallback
that reports `Skipped`, never `Completed`, for anything unclaimed). Every task attempt is recorded
in a durable `ExecutionHistory`; a `TaskExecutionRecord` marked `Completed` is never re-executed,
which is what makes both re-running the same context and calling `ResumeAsync` after a restart
behave identically and idempotently. Failures are classified into one of four kinds —
`Retryable` (auto-retried, capped), `Recoverable` (stop, wait to be resumed), `Fatal` (stop,
cannot resume), `OperatorActionRequired` (stop, needs a human) — and nine structured
`ExecutionEvent` types (`PhaseStarted`/`Completed`, `TaskStarted`/`Completed`, `RetryStarted`,
`ResumeStarted`, `FailureDetected`, `HealthVerified`, `CertificationCompleted`) give the runtime a
fully observable, no-unstructured-logging execution trail. `ExecutionProgress` folds all of this
into percent-complete, duration, ETA, warnings, errors, and retry count.

Rather than reimplementing provisioning logic a second time inside the new runtime — a real risk
with no compiler available to verify it — the Infrastructure phase's provisioner
(`ExistingInfrastructurePipelineTaskProvisioner`) adapts the existing, already-idempotent
`InfrastructureProvisioningPipeline` instead of duplicating it. Health and Certification phases
are backed by a new `IExecutionGateCheck` abstraction, kept deliberately free of any dependency on
Runtime Agent's own `IDockerProvider`/`IHealthProvider`/`IProfileManager` types; Runtime Agent's
one real composition (`RuntimeGateCheck`, in `ReleaseDeploymentProvider`) supplies the concrete
implementation, backed by the exact same provider calls `VerifyDeploymentAcceptanceAsync` already
uses. Upload, Configuration, and Deployment phase tasks are honestly reported `Skipped` — not
`Completed` — because their real work still runs through the existing, working, external
`Aovias.Orchestration` step sequence; subsuming that sequence into this runtime was judged a
materially larger, riskier redesign than this sprint's D1–D11 scope, and is called out prominently
in §9 and §10 rather than silently glossed over.

As with every M2.x report before this one, the sandbox this work was performed in has **no .NET
SDK, and every attempt to install one failed** (`curl https://dot.net/...` → HTTP 403
blocked-by-allowlist; `sudo apt-get install dotnet-sdk` → sudo disabled). No build and no test run
has been possible. Every claim of correctness here is a manual trace, not a green test run — see
§8 and §10 for what this means for merge readiness.

**Execution Context (D2).** Unlike `DeploymentPlan` (immutable, M2.4) or `AdmissionResult`
(immutable, M2.4), `DeploymentExecutionContext` is explicitly a live tracking record: every
provisioner the runtime calls in one run receives the exact same instance, so state one
provisioner records via `ProvisionerState` (e.g. the cached `InfrastructureReadinessReport`) is
visible to every later provisioner in the same run without threading extra parameters through the
runtime itself.

**Phase Executor / Task Executor (D3/D4).** These are not two separate classes — the brief's
"Phase Executor" and "Task Executor" concepts are the outer and inner loop of the same
`DeploymentExecutionRuntime.RunAsync`/`ExecuteWithRetryAsync` method pair. Splitting them into
separate types was considered and rejected: the two loops share one piece of state
(`ExecutionHistory`) and one termination rule ("stop the whole run the instant one task fails
without automatic recovery"), and a class boundary between them would only add an interface with
one implementation and one caller.

## 4. Execution Lifecycle

A full successful run walks:

`DeploymentPlan` (M2.4, already Approved + Validated)
→ `DeploymentExecutionContext` constructed (Runtime Agent composes this — see §2)
→ `DeploymentExecutionRuntime.ExecuteAsync`
→ for each of the eight phases, in `Plan.ExecutionPhases` order (`Preflight → Infrastructure →
  Upload → Configuration → Deployment → Health → Certification → Completion`):
  → `PhaseStarted` event
  → for each task, in `phase.Tasks` order:
    → `Registry.Resolve(task)` picks the one provisioner responsible
    → if already `Completed` in `History` and the provisioner trusts that (`CanResume`), skip
    → otherwise: `TaskStarted` event → `ExecuteTaskAsync` (retried per D10 if `Retryable`) →
      `ValidateResultAsync` is available to a provisioner internally but the runtime's own
      pass/fail decision is `outcome.Status` from `ExecuteTaskAsync` itself
    → on success: `TaskCompleted` event (+ `HealthVerified` if the phase is Health)
    → on failure: `FailureDetected` event, `CleanupAsync` (best-effort, exceptions swallowed),
      the whole run stops and returns immediately — no later phase or task is attempted
  → `PhaseCompleted` event (+ `CertificationCompleted` if the phase is Certification)
→ `ExecutionResult` assembled from the final `ExecutionHistory` and returned

Health Gates (D11) enforce this deterministically: a `PASS` lets the Health phase's tasks
complete normally and the run continues into Certification; a `FAIL` is classified `Recoverable`
by `HealthGateTaskProvisioner`, which stops the run there — the Certification phase is never
reached and `CertificationCompleted` is never emitted — exactly the "PASS → Continue, FAIL →
Recovery" behavior the brief specifies, verified by `Runtime_HealthGateFailure_StopsBeforeCertification`
in the D12 suite (§8).

## 5. Idempotency Strategy

Every provisioner's `ExecuteTaskAsync` must itself be safe to call twice against the same
already-provisioned target — the runtime does not make a provisioner idempotent, it depends on
each one already being idempotent, and then adds a second, cheaper layer (skip-on-resume) on top:

- **Filesystem** (`ExistingInfrastructurePipelineTaskProvisioner`, "infrastructure.create-filesystem-directories"):
  delegates to `InfrastructureProvisioningPipeline`'s Filesystem stage, which has used
  create-if-missing directory creation since M2.0 — calling it against directories that already
  exist is a no-op, not an error.
- **Docker / networking** (Health/Certification gates: "docker-provider-available",
  "active-profile-valid"): these are read-only availability checks (`IDockerProvider.IsAvailable`,
  `IProfileManager.ValidateActiveProfile()`), not provisioning actions — checking twice simply
  reads the same live state twice and cannot corrupt anything.
- **Secrets and certificates** (`ExistingInfrastructurePipelineTaskProvisioner`,
  "infrastructure.provision-secret-*" / "provision-certificate-*"): delegate to the pipeline's
  Secrets/Certificates stages, both already idempotent since M2.0–M2.1 (write-if-absent /
  reuse-if-present semantics) — this sprint did not change that behavior, only reused it.
- **Confirmation tasks** (`ConfirmationTaskProvisioner`, Preflight/Completion): stateless —
  `ExecuteTaskAsync` only restates an already-true fact ("admission approved this," "this task
  completed"), so calling it any number of times returns the same `Completed` outcome.

**The runtime's own idempotency layer**, on top of every provisioner's own idempotency:
`DeploymentExecutionRuntime.RunAsync` checks
`priorRecord?.Status == Completed && provisioner.CanResume(task, priorRecord)` before dispatching
a task at all. This is what `Runtime_ExecutingSamePlanTwice_IsIdempotent` (§8) verifies directly:
calling `ExecuteAsync` twice against the *same* `DeploymentExecutionContext` (same `History`)
never re-invokes any provisioner for a task already recorded `Completed` — the skip check catches
it before the provisioner is even resolved a second time. This is deliberately a belt-and-braces
design: even if a provisioner's own idempotency guarantee were ever violated by a future bug, the
skip check means the runtime still would not call it twice for the same completed task.

## 6. Resume & Recovery

**Checkpoint storage.** `ExecutionHistory` is the single durable record: a list of
`TaskExecutionRecord`s (one per attempted task, with `Status`/`Attempts`/`StartedUtc`/
`CompletedUtc`/`LastError`/`LastFailureClassification`) and a list of `ExecutionEvent`s. It has no
persistence mechanism of its own in this sprint (see §9) — a caller (Runtime Agent, or a future
scheduler) is responsible for persisting `ExecutionResult.History` somewhere durable between the
process that ran `ExecuteAsync` and the process that later calls `ResumeAsync`.

**Resume behavior (D7).** `ResumeAsync(context, priorHistory, ct)` copies every record and event
from `priorHistory` into `context.History`, emits `ResumeStarted` (with the last successful task
id in its message), then runs the exact same `RunAsync` loop `ExecuteAsync` uses. Because the
records are already present, the loop's `HasCompleted` skip check does the rest — no separate
"resume mode" branch exists in the phase/task loop itself, which is what guarantees a task
`priorHistory` already marks `Completed` is never re-executed on resume (verified by
`Runtime_Resume_DoesNotReExecuteAlreadyCompletedTasks`, §8).

**Retry behavior (D10).** Only failures classified `Retryable` are retried automatically, inside
the same `ExecuteAsync`/`ResumeAsync` call, up to `maxRetries` (default 3, constructor-configurable)
— gated additionally by `provisioner.CanRetry(task, record)`. `Recoverable`,
`OperatorActionRequired`, and `Fatal` failures are never auto-retried; they stop the run and rely
on a later `ResumeAsync` call (after whatever external fix was needed) to continue. `Fatal`
failures additionally set `CanResume = false` on the result — the one case where even `ResumeAsync`
should not be attempted again without a structural fix.

**Recovery strategy.** Every failure's classification is recorded on the `TaskExecutionRecord`
(`LastFailureClassification`) and folded into the returned `ExecutionResult.CanResume`, giving a
caller (an operator, a dashboard, an auto-resume scheduler) exactly the signal needed to decide
whether calling `ResumeAsync` is worthwhile at all before doing so.

**Example timeline — Retryable, auto-recovers:**
```
t0  Preflight/Infrastructure/Upload/Configuration all complete normally
t1  Deployment phase, task "deployment.start-gateway": attempt 1 fails (Retryable, transient port bind race)
t2  RetryStarted event; attempt 2 fails (Retryable)
t3  RetryStarted event; attempt 3 succeeds → TaskCompleted
t4  Deployment/Health/Certification/Completion complete normally
    → ExecutionResult.Success = true, Progress.RetryCount = 2
```

**Example timeline — Recoverable, requires resume:**
```
t0  Preflight/Infrastructure complete
t1  Upload phase, task "upload.extract-release": fails (Recoverable — disk full)
    → FailureDetected event; run stops; CanResume = true; ExecutionResult returned to caller
t2  (out of band: operator/automation frees disk space)
t3  Caller calls ResumeAsync(newContext, result.History)
    → ResumeStarted event; Preflight/Infrastructure tasks skipped (already Completed);
      "upload.extract-release" retried fresh (its own prior record was Failed, not Completed) → succeeds
t4  Upload/Configuration/Deployment/Health/Certification/Completion complete normally
    → second ExecutionResult.Success = true
```

**Example timeline — Fatal, cannot resume:**
```
t0  Preflight completes
t1  Infrastructure phase, task "infrastructure.create-filesystem-directories": fails (Fatal — no
    InfrastructureProvisioningContext was seeded into ProvisionerState by the caller — a
    composition bug, not a transient or externally-fixable condition)
    → FailureDetected event; run stops; CanResume = false
    → the caller must fix its own composition of DeploymentExecutionContext and start a brand new
      execution, not call ResumeAsync against this history
```

## 7. Progress & Events

**Progress model (D8).** `ExecutionProgress` is recomputed at the end of every run from the final
`ExecutionHistory`: `PercentComplete` (`Completed` task count ÷ total tasks across all phases,
`100` when there are no tasks at all), `Duration` (wall-clock since `context.StartedUtc`),
`EstimatedRemaining` (average per-task duration among completed tasks × remaining task count —
`null` until at least one task has completed, and `null` once everything has), `Warnings`
(accumulated `context.Diagnostics`, including every provisioner's own `TaskExecutionOutcome.Warnings`),
`Errors`, and `RetryCount` (sum of `Attempts - 1` across every recorded task, so a task that
succeeded on its third attempt contributes 2, not 3).

**Execution events (D9).** Nine structured types — `PhaseStarted`/`PhaseCompleted`,
`TaskStarted`/`TaskCompleted`, `RetryStarted`, `ResumeStarted`, `FailureDetected`,
`HealthVerified`, `CertificationCompleted` — every one carrying a timestamp, an optional phase, an
optional task id, and a human-readable message. There is no unstructured `Console.WriteLine`- or
bare-string-logging path anywhere inside `DeploymentExecutionRuntime` itself; every observable
runtime action becomes one of these nine event types, appended to `ExecutionHistory.Events` in
occurrence order.

**Event consumers / observability strategy.** In this sprint's one real integration,
`ReleaseDeploymentProvider` reads `ExecutionResult.Success`/`Progress.PercentComplete`/
`Progress.RetryCount` into the existing `DeploymentStepResult.Metadata` dictionary and logs every
`executionResult.Errors` entry via the provider's existing `ILogger` — the same
metadata-plus-structured-logging pattern the M2.4 Admission/Planning integration already
established, so no new observability plumbing (dashboards, metrics pipelines) needed inventing for
this sprint to be genuinely observable end to end. The full `ExecutionHistory.Events` list is
available on the `ExecutionResult` returned to any caller (today, only `ReleaseDeploymentProvider`)
that wants a richer trail than the summarized metadata — e.g., a future Deployment Workspace UI
consuming per-task timelines directly, which the model already supports without change.

## 8. Regression Results

**No test has been executed.** As in every M2.x report before this one: no .NET SDK is available
in this sandbox, and installing one is blocked at the network and OS-privilege level. The
following is a manual trace of what each new test asserts, not a report of a real test run.

New: `Aovias.DeploymentValidation.Tests/DeploymentExecutionRuntimeTests.cs` (D12), covering:

- **Phase execution**: a full run against a real, `DeploymentPlanBuilder`-produced plan visits all
  eight phases, in canonical order, verified via `PhaseStarted` event order.
- **Task execution / events**: every task in the plan emits exactly one `TaskStarted` and one
  `TaskCompleted` event on a clean run; `HealthVerified` and `CertificationCompleted` both fire
  when their phases complete via an `AlwaysPassGateCheck`.
- **Retry**: a task configured to fail twice then succeed is retried automatically (two
  `RetryStarted` events, `Progress.RetryCount == 2`, three total invocations); a task that never
  stops failing is retried exactly up to `maxRetries` (3) invocations and then stops with
  `Success == false`.
- **Failure recovery / classification**: a `Fatal` failure (no `InfrastructureProvisioningContext`
  seeded) reports `CanResume == false`; a `Recoverable` failure reports `CanResume == true` and is
  invoked exactly once (never auto-retried, unlike `Retryable`).
- **Health gates**: a failing `IExecutionGateCheck` stops the run before the Health phase's own
  `PhaseCompleted` event and before `CertificationCompleted` is ever emitted — the Certification
  phase is never reached.
- **Resume / idempotency**: a run that fails partway through (Configuration phase) and is then
  resumed with a fixed provisioner does not re-invoke the provisioner for the Preflight task
  already marked `Completed` before the failure, and emits `ResumeStarted`; calling `ExecuteAsync`
  twice against the very same context (simulating a duplicate trigger) does not re-invoke the
  provisioner for any task a second time.
- **Progress reporting**: a fully successful run reports `PercentComplete == 100`, an empty
  `Errors` list, and a non-negative `Duration`.
- **Cancellation**: calling `ExecuteAsync` with an already-cancelled token throws
  `OperationCanceledException` rather than returning a `Failed` `ExecutionResult` — cancellation is
  not folded into the failure-classification model, matching `ExecuteOneAttemptAsync`'s explicit
  `catch (OperationCanceledException) { throw; }` rethrow.

**Existing tests.** No existing test constructs `DeploymentExecutionRuntime`,
`InfrastructureTaskProvisionerRegistry`, or any of the new `Execution` namespace types (they did
not exist before this sprint), so there is nothing pre-existing for this sprint to have broken by
addition alone. `ReleaseDeploymentProvider`'s constructor signature is unchanged — the execution
wiring in `EnsureRuntimeFoldersAsync` uses only fields already present on the class
(`dockerProvider`, `healthProvider`, `profileManager`, `apiSettings`) plus locally-constructed
objects, so no DI registration needed to change. The pre-existing
`InfrastructureProvisioningPipeline` call inside `EnsureRuntimeFoldersAsync` is untouched — it
still runs first, exactly as before M2.5, and its report continues to feed both the M2.4 Admission
request and (newly, via the seeded `ProvisionerState` entry) the new
`ExistingInfrastructurePipelineTaskProvisioner`. `DeploymentAdmissionEngine`, `DeploymentPlanBuilder`,
and `DeploymentPlanValidator` (M2.4) are untouched; every M2.4 regression test
(`DeploymentAdmissionAndPlanningTests.cs`) remains valid.

Manual re-reading of the fully-edited `ReleaseDeploymentProvider.cs` (the same discipline that
caught a real scoping bug in M2.4) confirmed: the `provisioningContext` hoisting is consistent
(declared once, assigned once inside the `if (hostPaths is not null)` block, read once afterward
in the execution-wiring block); `RuntimeGateCheck`'s constructor parameters match the four fields
already present on `ReleaseDeploymentProvider`; the four `CertificationGate` ids
`DeploymentPlanBuilder.BuildCertificationGates` produces (`docker-provider-available`,
`health-provider-available`, `active-profile-valid`, `deployment-acceptance-health-check`) and the
one `HealthGate` id it produces (`primary-health-probe`) are exactly the ids `RuntimeGateCheck`'s
`switch` statement recognizes, with a safe `Pass()` default for any id it does not.

## 9. Technical Debt

- **Upload, Configuration, and Deployment phase tasks are honestly `Skipped`, not really executed
  by this runtime.** `PendingExternalExecutionTaskProvisioner` reports `Skipped` for every task in
  these three phases; their real work still runs through the existing, working, external
  `Aovias.Orchestration` step sequence (`ExtractReleaseAsync`, `StageReleaseAsync`,
  `LoadDockerImageAsync`, `BackupCurrentReleaseAsync`, `ActivateReleaseAsync`), which this sprint
  deliberately did not touch or redesign. This is the top item in this section and the top blocker
  flagged in §10: a `DeploymentPlan`'s Upload/Configuration/Deployment tasks currently describe
  work the Execution Runtime does not yet actually perform, only accounts for. **Recommend:
  prioritize in M2.6 or a dedicated follow-up** — either migrate those orchestrator steps into new
  `IInfrastructureTaskProvisioner` implementations (the natural, lowest-risk path, since the
  underlying step methods already exist and work), or explicitly redesign
  `Aovias.Orchestration` itself to become a caller of `IDeploymentExecutionRuntime` end to end.
- **Two coexisting per-task/per-stage provisioner interfaces.** `Execution.IInfrastructureTaskProvisioner`
  (new, this sprint) and `Infrastructure.Provisioners.IInfrastructureProvisioner` (M2.0–M2.4,
  unchanged) both exist, modeling related but different granularities — the older interface models
  one coarse readiness *stage* over an entire bundle; the new one models one `DeploymentTask` at a
  time, with a fuller lifecycle (execute/validate/resume/retry/cleanup/progress). This mirrors the
  same judgment call M2.4 made keeping `Planning.DeploymentPlanner` and `DeploymentPlanBuilder`
  coexisting. **Recommend: refactor in a future sprint** — once every phase genuinely executes
  through the new runtime (see the item above), the older interface's remaining callers
  (`DependencyInfrastructureProvisioner`, the shared DRV/Runtime Agent pipeline stage) could be
  revisited to determine whether they still need a separate abstraction.
- **`AlwaysPassGateCheck` is a real, shippable type in the shared library, not test-only-by-
  construction.** It is clearly documented as inappropriate for production use, but nothing at the
  type-system level currently prevents a future caller from wiring it in by mistake outside a test
  project. **Recommend: defer**, but flag clearly — a future hardening pass could move it into a
  test-only assembly, or add an `[Obsolete]`-style warning, if this risk is judged worth the extra
  friction.
- **`ExecutionHistory` has no persistence mechanism of its own.** `ResumeAsync` accepts a
  `priorHistory` parameter, but nothing in this sprint serializes an `ExecutionHistory` to durable
  storage between the process that produced it and whatever later calls `ResumeAsync` — that
  responsibility is left entirely to the caller. **Recommend: defer to M2.6** if
  "Autonomous Infrastructure Reconciliation & Self-Healing" needs unattended resume across process
  restarts, since that would be the first real consumer forcing a concrete answer to "where does
  history live between runs."
- **Task dependency chain is still the single linear chain M2.4 established**, not a true DAG —
  this sprint's Execution Runtime walks `phase.Tasks` in plan order and does not attempt any
  within-phase parallelism, which is consistent with (not a regression from) the M2.4 plan model's
  own documented limitation. **Recommend: defer**, unchanged from M2.4's own recommendation — no
  execution engine existed to exploit parallelism before this sprint, and this sprint's runtime
  still processes tasks strictly sequentially by design, so building a richer graph remains
  speculative until a real need for concurrent task execution emerges.
- **`ExistingInfrastructurePipelineTaskProvisioner.CanRetry` caps at 2 attempts, distinct from the
  runtime's own default of 3.** This was a deliberate per-provisioner choice (the underlying
  pipeline's own stages already retry internally in places, so a lower outer cap avoids
  compounding retries), but it means retry ceilings are not uniform across every provisioner in
  this sprint, which could surprise a future reader expecting one global constant to govern
  everything. **Recommend: defer**, but document prominently — this ceiling should be revisited
  once real retry telemetry exists to justify a specific number rather than a judgment call.

## 10. Readiness Assessment for M2.6 — Autonomous Infrastructure Reconciliation & Self-Healing

**What is ready:** the Execution Runtime this milestone was commissioned to build is real,
plan-driven, and structurally distinct from the decision-making layers M2.4 built — it consumes a
`DeploymentPlan` it never generates or modifies (Final Engineering Rule 3), and it never
re-evaluates whether a deployment is allowed (Final Engineering Rule 1). Idempotency, resume, and
retry are enforced in code — `HasCompleted`-gated skipping, a `Retryable`-only auto-retry loop
capped per provisioner, and a `ResumeAsync` that reuses the exact same phase/task loop
`ExecuteAsync` does — not merely documented as an intention. Structured events and progress give
M2.6 a genuinely observable execution trail to reconcile against: an autonomous self-healing
system built on top of this runtime would have `ExecutionHistory`, `FailureClassification`, and
`ExecutionEvent`s to reason from, rather than an ad hoc pass/fail signal.

**What is a genuine blocker:** the same one every M2.x report has disclosed — zero real build or
test runs across five consecutive sprints. This sprint's manual trace caught and fixed one real
compile-breaking gap before it could have shipped broken: the execution-wiring code inserted into
`ReleaseDeploymentProvider.cs` referenced a `RuntimeGateCheck` type that had not yet been written
into the file, discovered and fixed only through careful re-reading of the whole edited file, not
compilation. **M2.6 must not begin until this branch has been built and tested in a real .NET
environment.**

**A second, sprint-specific blocker for M2.6 specifically:** "Autonomous Infrastructure
Reconciliation & Self-Healing" almost certainly implies detecting drift and re-running (or
partially re-running) an execution without a human explicitly calling `ResumeAsync` — but with
Upload/Configuration/Deployment phases still `Skipped` rather than genuinely executed (§9, top
item), any self-healing logic built directly on top of this runtime today would only be able to
reconcile the Infrastructure/Health/Certification phases for real. Self-healing the phases that
still run through the external orchestrator would require either M2.6 or an earlier follow-up to
close that gap first.

**Recommended before M2.6 starts:**
1. Run `dotnet build` and `dotnet test` across the whole solution.
2. Decide whether closing the Upload/Configuration/Deployment execution gap (§9) is a
   prerequisite for M2.6 or explicitly part of M2.6's own scope — self-healing logic reasoning
   about phases the runtime does not yet really execute would be reasoning about incomplete data.
3. Decide where `ExecutionHistory` should be durably persisted between runs, since autonomous
   reconciliation implies resuming or re-evaluating executions without a human present to hold a
   `DeploymentExecutionContext` in memory across the gap.
4. Decide whether reconciliation/self-healing should be a new caller of
   `IDeploymentExecutionRuntime.ResumeAsync` on a schedule (the lowest-risk extension of what
   already exists) versus a new, separate decision layer that itself decides when to call it —
   the latter risks re-introducing exactly the "decision logic embedded in an execution path"
   problem M2.4 and M2.5 both worked to factor out.

With those addressed, the platform is architecturally ready for M2.6: a plan-driven, idempotent,
resumable, fully-evented execution runtime already exists and is already exercised by the one real
Runtime Agent entry point that needed it.
