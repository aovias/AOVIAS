# Sprint M2.2 — Contract Schema v2 & Versioned Migration Implementation Report

Date: 2026-07-05
Scope: Contract schema versioning, migration, and compatibility only. Requirement/Capability,
capability admission, a v2 infrastructure specification language, Kubernetes projection,
bootstrap redesign, runtime provisioning redesign, and environment registration are explicitly
out of scope and were not touched.

## 1. Executive Summary

M2.2 turns the infrastructure contract from a single fixed shape into a versioned, evolvable
artifact. Every contract now carries an explicit `schemaVersion` and a metadata envelope —
contract identity, compatibility range, migration provenance, an integrity content hash,
publishing engine version, source revision, and generated-UTC — wrapped around the same domain
model (filesystem, certificates, secrets, database, docker, network, storage, providers,
dependencies, health) Sprint M2.0/M2.1 already established. Publishing always emits schema v2.
`DeploymentPackageContractReader` — the single production read path since M2.0 — now detects the
schema version of whatever it is actually reading, migrates schema v1 (M2.0/M2.1) packages to
the current shape in memory through a new `IInfrastructureContractMigrator`, validates the
result, and returns the same unified `InfrastructureContract` type it always has. Runtime Agent
and DRV needed zero source changes: both already consume the contract exclusively through this
one reader, which is exactly what makes them "transparently consume supported versions" without
knowing versioning exists.

The compatibility decision (publisher schema vs. this build's supported ceiling) is centralized
in one pure function, `InfrastructureContractCompatibility.Evaluate`, implementing the four-row
matrix the sprint specifies (Pass / AutoMigrate / Fail / Fail) so that introducing a v3 schema
later is a matter of registering a new migrator, not re-deriving this decision. Migration never
mutates a package on disk, and — a deliberate, documented departure from a literal reading of
"Migration Metadata" — never stamps a wall-clock time either, because two independent reads of
the same immutable package (Runtime Agent and DRV) must migrate to byte-identical output, and a
read-time clock stamp would silently break that existing M2.0 guarantee.

## 3. Schema v2 Specification

### 3.1 Field definitions

| Field | Type | Meaning | Present for migrated (v1) contracts? |
|---|---|---|---|
| `schemaVersion` | int | The wire schema version. Defaults to `1` in code specifically so an absent key is read as legacy. | Always `2` after migration — the envelope always describes the object's *current* shape, not its origin. |
| `contractVersion` | string | Semantic content version string (`"1.0"` or `"2.0"`), kept alongside `schemaVersion` as a second, human-readable confirmation the reader cross-checks. | `"2.0"` |
| `identity` | object | `{ serviceId, serviceVersion }` — which service and version this contract belongs to. | `serviceVersion` is `null`: schema v1 never carried a service version inside `infrastructure.contract.json`. |
| `compatibility` | object | `{ minimumSupportedSchemaVersion, maximumSupportedSchemaVersion }` — a self-describing echo of `ContractSchemaVersions` at the moment this instance was produced. | Always `{1, 2}` — describes this build's range, not the artifact's origin. |
| `migration` | object or null | `{ migratedFromSchemaVersion, migratorId }`, present only if this instance was produced by a migrator. Deliberately carries no timestamp — see §4 and the policy document §4. | Present. |
| `integrity` | object | `{ hashAlgorithm, contentHash }` — SHA-256 over the domain payload only, independent of the package-level checksum. | Present, computed from the migrated domain content. |
| `publishingEngineVersion` | string | The Publishing engine build that compiled this contract. | Empty — not recoverable from a v1 payload. |
| `sourceRevision` | string | The deterministic source revision of the publish run. | Empty — not recoverable from a v1 payload. |
| `generatedUtc` | DateTimeOffset | When Publishing generated this contract, taken from the fixed build identity of that publish run. | Default (`0001-01-01T00:00:00+00:00`) — not recoverable from a v1 payload. |
| `serviceId` … `health` | (unchanged) | The existing domain model — filesystem, certificates, secrets, database, docker, network, storage, providers, dependencies, health. | Copied across unchanged. |

Every field above is documented a second time, in context, in `docs/milestones/CONTRACT-SCHEMA-EVOLUTION-POLICY.md` §1–§4, which is the document future schema revisions are expected to extend.

### 3.2 Versioning

`schemaVersion` and `contractVersion` are intentionally two different axes: `schemaVersion` is
the coarse wire-shape major version the reader branches on; `contractVersion` is a semantic
string that moves in lockstep with it today but is free to gain minor values later (e.g.
`"2.1"`) for additive changes that do not require a migrator. This sprint bumps `contractVersion`
for the infrastructure contract specifically, via a new dedicated constant
(`ContractSchemaVersions.ContractVersionV2`) rather than reusing the platform-wide
`ServiceContractBuilder.ContractVersion` constant, which still governs `deployment.contract.json`
and the identity contract and remains `"1.0"` — deliberately out of this sprint's blast radius
(see Technical Debt).

### 3.3 Serialization rules (D2)

- Publishing always emits `schemaVersion: 2` explicitly (`InfrastructureSpecificationCompiler`
  never relies on a default).
- Serialization is fully deterministic given the same inputs: `GeneratedUtc` comes from the
  publish run's fixed `PublishingBuildIdentity.BuildUtc`, established once per run, never a fresh
  `DateTimeOffset.UtcNow` read inside the compiler or at write time.
- `InfrastructureContractPublisher.ValidateBeforeWrite` independently re-serializes the compiled
  contract twice and requires the two outputs to be byte-identical, as a direct, literal check of
  "the serialization format must remain deterministic" before anything is written to disk.
- No runtime-generated fields: every field on a natively-compiled contract is a pure function of
  the specification, the bundle, and the fixed `ContractPublishingMetadata` — nothing is derived
  from ambient state at serialization time.

## 4. Migration Architecture

```
Publishing (native path, schema v2)                  Runtime Agent / DRV (read path)
─────────────────────────────────────                ───────────────────────────────
Infrastructure Specification (M2.1)                   .aovdeploy / staging directory
        │                                                       │
        ▼                                              DeploymentPackageContractReader
InfrastructureSpecificationCompiler                              │
        │ stamps schema v2 envelope                    checksum verified (ICA004/005)
        ▼                                                       │
InfrastructureContractPublisher                          ProbeSchemaVersion (schemaVersion probe)
   (ValidateBeforeWrite; D6)                                     │
        │                                          InfrastructureContractCompatibility.Evaluate
        ▼                                             ┌──────────┼──────────┐
infrastructure.contract.json                        Pass     AutoMigrate    Fail
   (schema v2, checksummed)                            │          │          │
                                                 ReadNative   Migrate(...)  ICA010
                                              (round-trip   (round-trip against
                                               against v2)   InfrastructureContractV1,
                                                             then IInfrastructureContractMigrator)
                                                        │          │
                                                        └────┬─────┘
                                                             ▼
                                                  InfrastructureContract (schema v2, unified)
                                                             │
                                                             ▼
                                          InfrastructureProvisioningPipeline (unaware of migration)
```

**Migrators.** `IInfrastructureContractMigrator` exposes `FromSchemaVersion` and
`Migrate(InfrastructureContractV1) → InfrastructureContract`. Exactly one is registered today,
`InfrastructureContractV1ToV2Migrator`, in a private dictionary inside
`DeploymentPackageContractReader` keyed by schema version. It copies every domain object across
by reference (proven by `Migration_PreservesDomainContentExactly`, which asserts
`Assert.Same` on each domain field), stamps `Migration` provenance, computes
`Integrity.ContentHash`, and leaves `PublishingEngineVersion`/`SourceRevision`/`GeneratedUtc` at
honest empty/default values rather than fabricating data schema v1 never carried.

**Compatibility layer.** `InfrastructureContractCompatibility.Evaluate(publisherSchemaVersion,
runtimeMaxSupportedSchemaVersion, runtimeMigratableFromVersions)` is a pure function with no
dependency on the reader, so it is unit-testable in isolation (§5) and is the only place the
Pass/AutoMigrate/Fail decision is made — the reader calls it, and switches on the result.

**Runtime reader.** `DeploymentPackageContractReader.ValidateAndDeserialize` now: (1) verifies
the package-level SHA-256 checksum exactly as it always has, unaffected by schema version; (2)
probes `schemaVersion` via a minimal DTO, catching malformed JSON or a non-numeric value as
`ICA006`; (3) asks the compatibility evaluator what to do; (4) on `Pass`, deserializes directly
into `InfrastructureContract` and requires a byte-for-byte round trip against *that* shape; (5)
on `AutoMigrate`, deserializes into `InfrastructureContractV1` and requires the round trip against
*that* (legacy) shape first — preserving the exact ICA009 tamper-detection guarantee a v1 package
has always had — then hands the untouched legacy object to the migrator and validates the result
(`ICA011` if the migrator did not produce a valid current-schema object); (6) on `Fail`, throws
`ICA010` with the evaluator's own explanation as the message. Provisioning
(`InfrastructureProvisioningPipeline`, `ReleaseDeploymentProvider`, DRV's validation stages) calls
only `ReadFromPackage`/`ReadFromDirectory` and receives the unified `InfrastructureContract` —
none of them required a source change, which is the literal meaning of "provisioning must remain
unaware of migration."

## 5. Compatibility Matrix

| Publisher schema | Runtime's max supported schema | Result | Realized in this codebase as |
|---|---|---|---|
| v2 | v2 | **Pass** | The reader's default path for every contract Publishing writes today. |
| v1 | v2 | **AutoMigrate** | The reader's default path for every M1/M2.0/M2.1 package still on disk. |
| v2 | v1 | **Fail** | `InfrastructureContractCompatibility.Evaluate(2, 1)` — see below. |
| Unknown (≤ 0, or any value with no registered migrator and above the ceiling check) | any | **Fail** | `Evaluate(0, 2)`, `Evaluate(-1, 2)`, `Evaluate(99, 2)`. |

**On the "v2 publisher / v1 runtime" row:** this codebase ships exactly one reader, whose ceiling
is always `ContractSchemaVersions.Current`. There is no second, older Runtime Agent binary to
observe failing in this test suite. The row is instead proven directly against the evaluator —
`CompatibilityMatrix_DowngradeScenario_NewerPublisherFailsOlderRuntime` calls
`Evaluate(publisherSchemaVersion: 2, runtimeMaxSupportedSchemaVersion: 1)` and asserts `Fail` —
which is the honest scope of what can be demonstrated without an actual outdated agent build. The
policy document (§3) records this scoping explicitly so it isn't mistaken for untested behavior.

**Rejection behavior:** every `Fail` outcome raises `DeploymentPackageContractException` with a
deterministic code (`ICA010` for a version the compatibility evaluator rejects, `ICA011` for a
migration that produced an invalid result, `ICA006`/`ICA007`/`ICA009` unchanged from M2.0 for
JSON errors, contract-version mismatches, and tamper detection respectively). No code path
returns a partially-migrated or best-effort contract — every failure is a hard stop.

## 6. Equality Verification

Migration must preserve semantic meaning (D7). This is proven two ways:

1. **`CanonicalEquality_MigratedV1MatchesNativeV2_ForTheSameDeclaredInfrastructure`** builds one
   domain payload (via the same `InfrastructureContractBuilder.Build` call site the M2.0-era
   tests already used), wraps it once as a hand-built schema v1 object and once as a hand-built
   native schema v2 object, migrates the former, and asserts
   `InfrastructureContractIntegrity.ComputeContentHash` is identical between the migrated result
   and the native one — even though their envelopes differ (the native one has a service version
   and non-empty engine/revision fields; the migrated one does not). The hash is computed only
   over the domain payload (`ContractDomainSnapshot`), with `contractVersion` normalized to the
   current value in the snapshot specifically so the version *label* — envelope metadata — never
   participates in a domain-equality decision.
2. **`CanonicalEquality_DetectsADeliberateSemanticDifference`** takes the same native contract,
   changes exactly one domain field (`Health.HealthUrl`), and asserts the content hash now
   *differs* from the migrated contract's — proving the hash is sensitive to real content
   changes and not a constant that would make the first test vacuously true.

The same content-hash mechanism additionally re-verifies the M2.1 golden-equivalence test
(`Compiler_output_is_functionally_equivalent_to_previous_hardcoded_builder`), which now compares
the new compiler's output against the legacy hardcoded builder's output by content hash rather
than full-object serialization, since the two now legitimately differ in envelope but must still
never differ in the infrastructure they describe.

## 8. Migration Policy

See `docs/milestones/CONTRACT-SCHEMA-EVOLUTION-POLICY.md` for the full, durable policy this sprint
establishes as the reference for all future schema work. Summary:

- **Upgrade strategy:** a new schema version gets a new migrator chained from the immediately
  previous version (v2→v3, not v1→v3), a bump to `ContractSchemaVersions.Current`, compiler
  changes to stamp the new envelope, and the same shape of regression suite this sprint adds.
- **Deprecation policy:** a version remains Supported (legacy, migratable) for at least one full
  milestone after it stops being Current before it may be Removed; Removal deletes its migrator
  and drops it from `ContractSchemaVersions.Supported`, after which reading it deterministically
  fails (`ICA010`) rather than being silently migrated forever.
- **Future schema evolution process:** the seven-step upgrade path in the policy document §5.

## 9. Technical Debt

| Item | Disposition |
|---|---|
| `ContractMigrationMetadata` carries no timestamp | Deliberate, documented (§4, policy doc §4) — not a gap, but a constraint every future migrator must also respect. |
| `Identity.ServiceVersion`, `PublishingEngineVersion`, `SourceRevision`, `GeneratedUtc` are empty/default on migrated contracts | Honest consequence of schema v1 never carrying this data; not fabricated. If this data is later needed for migrated contracts too, it would have to come from a different source (e.g. cross-referencing `deployment.contract.json`'s `Version`), which is a larger design change than this sprint's scope. |
| `ServiceContractBuilder.ContractVersion` (governs `deployment.contract.json`, the identity contract, and the manifest) remains `"1.0"`, independent of the infrastructure contract's new `"2.0"` | Deliberately out of this sprint's blast radius, but leaves "contract version" meaning two different things depending on which file is being read. Should be reconciled — or explicitly and permanently scoped as two independent version axes — before Requirement/Capability work touches either. |
| No machine-validated JSON Schema artifact for schema v2 (only C# types + XML doc + the policy document) | The original milestone architecture document's Layer 0 called for a published JSON Schema artifact. This sprint documents the schema thoroughly in prose and types but does not emit a `.schema.json` file. Needed only if external tooling (not this codebase) must validate contracts without loading the .NET assembly. |
| `Migrators` is a private `static readonly` dictionary literal inside the reader, not DI-registered | Fine at one migrator; the policy document (§2) flags this as worth revisiting, not as a defect, if the registered-migrator count grows. |
| `InfrastructureContractBuilder` (M2.0-era hardcoded builder) still exists, still produces implicit schema v1 shape by default, still exercised only by pre-M2.1 unit tests | Same debt item carried from the M2.1 report, now also the source of every "legacy v1" domain payload this sprint's new tests build from — its removal is contingent on migrating those tests to the specification compiler, as M2.1's report already recommended. |
| No "deprecated version" warning-on-read mechanism | The lifecycle policy (§1) defines a Deprecated stage between Supported and Removed, but nothing in `DeploymentPackageContractReader` currently surfaces a warning for a deprecated (still-migratable) version — today there is only Current/Supported/Removed in code, with Deprecated existing purely as a documented intention. |
| Sandbox could not execute a build or test run (§7) | Carried forward from M2.1; still unresolved in this environment. |
| M2.0's own pre-M2.1 build-health blockers (`DeploymentHostSettings` compile break, `ValidateNeutralTemplate` signature mismatch, XML-documentation errors, two Windows path-separator test failures) | Never confirmed repaired across M2.1 or M2.2; still open as far as this report can verify. |

## 10. Readiness Assessment

**Ready for Sprint M2.3 (Requirement & Capability Infrastructure Model) on the schema/versioning
axis:** every contract now declares its schema version explicitly; Publishing is the only
compiler and always emits the current schema; migration is deterministic, auditable (via
`MigratorId`/`MigratedFromSchemaVersion`), and centralized behind one compatibility evaluator;
Runtime Agent and DRV required no changes to keep working; canonical equality between migrated
and native contracts is proven by a reusable content-hash mechanism that M2.3's own equality
needs (if any) can reuse directly.

**Blockers to close before M2.3 work should begin, in order of severity:**

1. **Execute the full build and test suite on a machine with the .NET SDK.** Identical caveat to
   the M2.1 report — nothing in §5–§7 has been confirmed by an actual `dotnet test` run in this
   delivery.
2. **Resolve the `ContractVersion` terminology split** (Technical Debt) before M2.3 introduces
   Requirement/Capability types that will need their own versioning story — better to have one
   coherent "what does 'contract version' mean" answer before a third axis is added.
3. **Carry forward the M2.0-era build-health blockers** (`DeploymentHostSettings`,
   `ValidateNeutralTemplate`, XML documentation, path-separator tests) — still unverified as
   fixed after two subsequent sprints.
4. **Decide whether a formal JSON Schema artifact is required** before any non-.NET tooling is
   expected to validate contracts independently; if yes, it is a small, additive task against the
   now-stable v2 envelope, not an architectural change.

None of these blockers are schema or migration defects; the versioning architecture itself —
envelope, migrator, compatibility matrix, reader integration, and canonical-equality proof — is
complete and, on manual trace, correct. It is ready to carry the Requirement/Capability model in
M2.3 once the above are cleared, in particular the actual test execution this sandbox could not
perform.
