# Sprint M3.3 — End-to-End Platform Integration — Implementation Report

**Scope note:** an earlier, pre-`ROADMAP_STATUS_REVIEW.md`-correction session used the "M3.3" label for different work (a "unified verification pipeline" — the `PlatformVerificationPipeline`/`DeploymentLifecycleReadinessVerifier` classes referenced throughout this report as existing production code). This report is for the M3.3 now sequenced after the corrected M3.0→M3.1→M3.2 baseline: **End-to-End Platform Integration**, tracing and integration-testing the full deployment pipeline as a single chain. Following the M3.1/M3.2 precedent, this is recorded as its own file since it is a distinct sprint scope under the same number, not a duplicate.

## 1. Executive Summary

This sandbox still has no .NET SDK, no sudo, and — newly clarified this sprint — network egress that is **not** a total connectivity failure but a **deliberate, policy-based allowlist block**: the egress proxy (port 3128, reachable) returns `403 Forbidden` with header `X-Proxy-Error: blocked-by-allowlist` for `nuget.org`, `dot.net`, `packages.microsoft.com`, `github.com`, and every other tested CDN/registry host. (This corrects the M3.1/M3.2 reports' framing of "total connection failure" — the earlier compact `curl` probes masked the proxy's real 403 response; a verbose re-test this sprint surfaced it. Practical effect is unchanged: SDK acquisition remains impossible, no cached SDK exists, `sudo` is refused.) No Ubuntu VPS target is available either. **Literal runtime execution of any pipeline stage is Blocked**, exactly as it has been every sprint since M3.0.

In place of execution, this sprint traced the actual cross-stage wiring — not single-file compile correctness (M3.1) or single-project test-logic correctness (M3.2), but whether one stage's output is genuinely what the next stage's code reads — across all 14 stages in the brief's pipeline diagram. **Two genuine, previously-undetected integration defects were found and fixed**, both reused-not-duplicated fixes to existing components: (1) `EnvironmentRegistrationSettings` (Sprint M4.3) had no `settings.*.json` file mapping at all, so a bootstrapped Runtime Agent's automatic re-registration-on-restart could never activate; (2) the M4.4 environment-level Deployment Ready report was computed and persisted but never actually consulted before a deployment executed — a real deployment could proceed into a knowingly-not-ready environment. One recurring environment artifact (bash-mount staleness on `DependencyInjection.cs`, previously documented in M3.0/M3.1) produced a third false-positive finding, disproven the same way as before. Two lower-confidence findings (a possible Bootstrap container-startup race, and an apparent Bootstrap/ReleaseManager path mismatch that turned out to be two intentionally-separate subsystems) are documented, not fixed, per this sprint's "fix only issues required" rule.

## 4. Integration Issues Fixed (grouped by root cause)

1. **Missing configuration-file mapping (root cause: an enumerated map was never extended when Sprint M4.3 added a new settings class).** `EnvironmentRegistrationSettings.SectionName` had no entry in `ProfileConfigurationLoader.FileSectionMap`, so no `settings.*.json` file — however named — could ever populate it through the profile-configuration convention every other settings class relies on. Compounded by Bootstrap never generating such a file even before that gap was found. Fixed both halves together (§2): the map now includes the section, and `BootstrapOrchestrator` now generates and uploads the file using values Bootstrap already possesses. Without this fix, Sprint M4.3's stated goal ("no external tool or operator step required" for registration to survive a restart) silently didn't hold for any bootstrapped-not-hand-configured environment.

2. **Computed-but-unconsulted state (root cause: Sprint M4.4 was explicitly scoped, in its own report, as publishing a status surface to Command Center — not as gating deployment execution — while `ROADMAP.md`'s own M4.4 acceptance line ("unmet requirement blocks with recovery text") implied a hard gate).** `EnvironmentAdmissionStore`'s persisted report was reachable only via heartbeat telemetry and a read-only API endpoint; `PlatformDeploymentService`/`ReleaseDeploymentProvider`'s actual execution path never read it. Fixed by adding one check in `ReleaseDeploymentProvider.EnsureRuntimeFoldersAsync`, reusing the existing store with no new evaluation logic — consistent with "reuse, don't duplicate."

3. **Recurring false positive (root cause: this sandbox's bash-mounted view of files edited via this program's own tools earlier in the same session serves stale, truncated content — documented in M3.0 and M3.1, now confirmed a third time).** One parallel research pass reported `Aovias.Runtime.Agent.Infrastructure/DependencyInjection.cs` truncated with `EnvironmentRegistrationHostedService` unregistered; a second pass in the *same batch* read the same file and reported the registration present. Direct `Read`-tool inspection (authoritative, per the established M3.0/M3.1 rule) confirmed the file is complete and the registration exists at line 115. No code change — disproven, not fixed.

## 5. Remaining Runtime Blockers

- **⛔ Blocked (policy-based egress allowlist, no sudo, no cached SDK):** every stage requiring `dotnet`/`docker`/a real host. Root cause refined this sprint: the proxy (reachable, port 3128) returns `403 blocked-by-allowlist` for nuget.org/dot.net/GitHub/Microsoft package CDNs specifically — an intentional network policy, not a connectivity failure. This is a more actionable fact for whoever controls the sandbox's egress allowlist than "no network" was.
- **⚠ Documented, not fixed — Bootstrap container-startup timing:** `RunRuntimeAgentInstallationAsync` issues `docker run -d` and returns immediately; `RunRuntimeAgentRegistrationAsync` (the next phase) calls the Runtime Agent's own endpoints with no health-poll/backoff first. A slow-starting container could make phase 7 fail before the process is actually ready to accept requests. Not fixed this sprint: the orchestrator's existing per-phase idempotent-resume design (a re-run only retries the failed phase, and the target is normally ready within the SSH round-trip's own latency) mitigates this without a code change, and adding a new poll/backoff loop to a "Zero-Touch" flow without a compiler available to verify it carries more risk than the finding's currently-unconfirmed severity justifies. Recommended for observation once a real VPS is available (M3.4).
- **Clarified, not a defect — Bootstrap's `deploy` verb vs. the Release Library pipeline:** an initial trace suspected a path mismatch between Bootstrap's SSH-push-to-`IncomingFolder` and the Release Library's own `IncomingRoot`. Re-reading both code paths in full showed these are two independent, both-functioning subsystems that were never meant to connect: the pre-existing `deploy` verb (unchanged since before M4.1) does a direct SSH-push-and-`docker compose up` with no Release Library/Admission/Planning involvement at all, while ongoing application deployments go through the entirely separate `ReleaseManagerService` → Release Library → `ReleaseDeploymentProvider` chain this report's stages 9–14 actually trace. Recorded here so this isn't re-discovered as a false alarm in a future sprint.
- **No direct unit-test harness for `ReleaseDeploymentProvider`** (pre-existing gap, not introduced this sprint) — the class most central to stages 9–14 has no dedicated test file; its 26 constructor dependencies make building a first fake harness a substantial undertaking on its own. Flagged for `IMPLEMENTATION_GUIDELINES.md` §5's testing bar, deferred rather than rushed without a compiler to validate a new, large fake.

## 6. Runtime Validation Prerequisites

Before Sprint M3.4 can produce anything beyond more source-level tracing, the following must exist somewhere real (this sandbox or elsewhhere):

1. A .NET 10 SDK reachable either by adding `nuget.org`/`dot.net`/`dotnetcli.blob.core.windows.net`/`packages.microsoft.com` to this sandbox's egress allowlist, or by running the pipeline on a machine that already has the SDK (the user's own machine or a CI runner).
2. A disposable or real Ubuntu VPS reachable over SSH (`ssh` client is present in this sandbox; nothing else needed on this side once a target and credentials exist) — or, at minimum, a local Docker host to exercise stages 5–14 without a full remote bootstrap.
3. Once both exist: run `dotnet restore && dotnet build Aovias.Platform.slnx` first (Build stage) — only after that is green does `dotnet test` (Test stage) become meaningful, and only after that does an actual `aovias-bootstrap bootstrap` run against the VPS (Runtime stage) become meaningful, per `IMPLEMENTATION_GUIDELINES.md` §12's progression.
4. The two fixes in §4 (##1, #2) should be the first things checked on that first real run — they are the two places this sprint changed behavior that source review alone cannot fully prove correct.

## 7. Readiness Assessment for Sprint M3.4 — Runtime Validation & Platform Certification

Source-level readiness is good and measurably improved by this sprint: two genuine cross-stage wiring gaps that would have silently undermined M3.4's own goals (an environment that can't durably re-register itself; a deployment that can proceed into a knowingly-unready environment) are now closed at the source level. Every one of the 14 diagrammed stages has been traced end to end at least once; none has ever been Runtime- or End-to-End-verified in this program. M3.4 is squarely blocked on the same prerequisite this sprint could not clear: a real SDK and a real target. Per `IMPLEMENTATION_GUIDELINES.md` §12, M3.4 should not be reported as advancing the roadmap on source analysis alone — its own acceptance bar requires the evidence tiers this sandbox cannot produce, and that must be stated as plainly in that report as it is here. No ADR was violated or changed; no new capability was introduced; both fixes reuse existing, already-shipped components exactly as the sprint's rules require.
