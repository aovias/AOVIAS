## 1. Executive Summary

Sprint M1.2 makes the publishing engine **provably deterministic at the package-content level** by introducing:

- A **Publishing Input Fingerprint** derived from canonical publish inputs (source revision, profile, templates, contracts, compose, Docker image identity).
- A single **Publishing Build Identity** established once per publish run and propagated to `manifest.json`, `metadata.json`, `publishing-build-manifest.json`, and publishing reports.
- **Fingerprint Policy v1** with streaming hashes, volatile-entry exclusion, and **Docker image identity** (not `service-image.tar` bytes) for fingerprinting.
- **Deterministic Docker cache invalidation** via content-derived `SOURCE_REVISION` / fixed `BUILD_UTC` build args for all services (replacing runtime-agent-only random GUID + `--no-cache`).
- **Pre-packaging staging integrity validation** and strengthened package checksum/orphan detection.
- **Regression tests** for fingerprint stability, input sensitivity, image-identity semantics, and stale-artifact rejection.

No contract origination, compose neutrality, release-library redesign, Runtime Agent, or infrastructure contract work was implemented (M1.3+).

## 3. Publishing Fingerprint Design

### Structure

Two related fingerprints:

| Fingerprint | Scope | When computed |
|-------------|-------|---------------|
| **Source Revision** | Publish-determining source (project file, publish output, Dockerfile, optional git commit) | Before Docker build |
| **Publishing Input Fingerprint** | Full publish inputs including profile, templates, compose, contracts, Docker image identity | Before packaging |
| **Package Fingerprint** | Deterministic hash of package contents per `FingerprintPolicy` v1 | Package verification |

### Inputs (canonical sorted key=value pairs → SHA-256)

**Source revision:** `project`, `dockerfile`, `publishOutput`, optional `gitCommit`

**Publishing input fingerprint:** `sourceRevision`, `serviceId`, `version`, `profile`, `buildConfiguration`, `framework`, `runtimeIdentifier`, `fingerprintPolicyVersion`, optional `gitCommit`, `dockerImageIdentity`, `configTemplate`, `envTemplate`, `compose`, `contracts`

### Hashing strategy

- **Text artifacts:** timestamp normalization (`TIMESTAMP` placeholder) for JSON/YAML/templates; contracts canonicalized JSON.
- **Binary artifacts:** streaming raw SHA-256 (no UTF-8 normalization).
- **`service-image.tar`:** excluded from byte hash; fingerprint uses `identity:{DockerImageIdentity}` from `manifest.json`.
- **Volatile entries (excluded):** `metadata.json`, `deployment-readiness.json`, `publishing-report.json`, `publishing-build-manifest.json`.

### Determinism guarantees

- Identical inputs ⇒ identical source revision and input fingerprint.
- Identical package contents + image identity ⇒ identical package fingerprint regardless of tar bytes or volatile timestamps.
- Changed compose/contracts/image identity ⇒ changed fingerprints.

## 4. Build Identity Design

### Fields

| Field | Lifetime | Stored in |
|-------|----------|-----------|
| `SourceRevision` | Fixed at pre-Docker establish | manifest, metadata, build manifest |
| `BuildUtc` | Fixed once at establish | build manifest (volatile for package fingerprint) |
| `BuildVersion` | From request / policy default | all artifacts |
| `PublishingInputFingerprint` | Finalized pre-packaging | manifest, metadata, build manifest, report |
| `DockerImageIdentity` | Set post-`docker build` | manifest, metadata, build manifest, report |
| `PackageFingerprint` | Set at package verification | context + report |
| `FingerprintPolicyVersion` | Constant `1` | metadata, build manifest |
| `PublishingEngineVersion` | From `PublishingVersionPolicy` | metadata, build manifest, report |

### Consumers

| Consumer | Usage |
|----------|-------|
| `PublishingStageExecutor` | Creates and updates identity through pipeline |
| `DeployPackageBuilder` / staging | Metadata + build manifest |
| `PackageVerifier` | Validates manifest ↔ metadata ↔ fingerprint consistency |
| `PublishingReportBuilder` | Operator-visible traceability |
| `GoldenPackageRepository` | Compares **package fingerprint** (existing gate; requires re-baseline) |

### Validation

- `PublishingStagingIntegrityValidator` — manifest traceability vs identity; orphan/stale staging detection.
- `PackageVerifier.ValidateBuildManifestConsistency` — build manifest required; fields must match metadata.
- `DeployPackageVerifier` — checksum completeness + orphan zip entries.

## 5. Artifact Traceability Matrix

| Artifact | Generated By | Fingerprint | Validation |
|----------|--------------|-------------|------------|
| `manifest.json` | `DeployManifestGenerator` + identity patch | Input fingerprint + image identity fields hashed in package fingerprint | Staging integrity + checksums |
| `metadata.json` | `PublishingStageExecutor` / `DeployPackageBuilder` | Volatile (excluded); carries identity fields for audit | Required file + publisher check |
| `publishing-build-manifest.json` | `PublishingBuildManifestWriter` | Volatile (excluded) | Required at verification; consistency with metadata |
| `docker-compose.yml` | `ComposeGenerator` | Normalized text hash in package fingerprint | Checksums + mount validation |
| Contract JSON files | `ServiceContractGenerator` | Canonical JSON hash | Contract validator + checksums |
| `service-image.tar` | `docker save` | **Image identity** (not tar bytes) | Protected-copy (M1.1) + identity resolution |
| `checksums.json` | `DeployPackageBuilder` | Self-referential (excluded from self-hash) | `DeployPackageVerifier` streaming verify |
| `*.aovdeploy` | `DeployPackageBuilder` | Package fingerprint | `DeterministicPackageFingerprint` + golden compare |
| Publishing report | `PublishingReportBuilder` | Volatile | Exposes fingerprints for operators |

## 6. Determinism Verification Results

### Automated evidence (CI)

| Scenario | Result |
|----------|--------|
| Identical sample packages | Same package fingerprint |
| Different compose | Different fingerprint |
| Different Docker image identity | Different fingerprint |
| Different tar bytes, same identity | **Same** fingerprint |
| Different metadata timestamps | **Same** fingerprint (volatile) |
| Identical publish inputs | Same source revision |
| Changed publish output | Different source revision |
| Changed compose input fingerprint inputs | Different input fingerprint |
| Stale manifest source revision in staging | Validation **fails** |

### Expected intentional non-determinism (documented)

| Field | Reason |
|-------|--------|
| `metadata.json` `CreatedUtc` | Audit timestamp |
| `deployment-readiness.json` | Certificate validation IDs/timestamps |
| `publishing-report.json` `GeneratedUtc` | Operator report timestamp |
| `publishing-build-manifest.json` `BuildUtc` | Build audit timestamp |
| `.aovdeploy` zip bytes | Zip timestamps (content fingerprint is authoritative) |

### Full double-publish E2E

Not executed in CI (requires Docker + fixture services). Unit/regression tests prove fingerprint semantics; full 10-service double-publish remains the Milestone 1 exit gate (Step 9).

## 9. Risk Assessment (before M1.3)

| Risk | Severity | Mitigation |
|------|----------|------------|
| Golden packages invalidated by fingerprint algorithm change | **High (expected)** | One-time re-baseline before enforcing golden gate in production |
| Non-runtime-agent images lack in-image build manifest verification | Medium | Image identity + source revision build args; full in-image manifest generalization is M1 Step 3 |
| `BUILD_UTC` still passed to Docker builds | Low | Fixed per publish run; excluded from package fingerprint via volatile manifest |
| Compose/profile concrete paths still affect input fingerprint | Medium | Expected until M1.5 compose neutrality |
| Git unavailable | Low | Falls back to content-only source revision |

## 10. Readiness Assessment for Sprint M1.3

**Verdict: Ready for M1.3 — Contract-Driven Publishing**

**Foundations in place:**

- Single pipeline with authoritative build identity and fingerprint policy.
- Package fingerprint is content-truthful (image identity, streaming hashes, volatile policy).
