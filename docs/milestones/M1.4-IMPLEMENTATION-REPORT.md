## 1. Executive Summary

This sprint set out to make `.aovdeploy` packages deployable to Local, Demo, QA, UAT, Production, and customer installations without rebuilding. Auditing the pipeline against that goal found something important: **most of the environment-neutrality work was already implemented**, apparently mid-flight from an unreported prior session — `ComposeDocumentBuilder`, `ServiceContractRegistry`, the `.env.template` generator, `DeploymentArtifactSanitizer`, a dedicated `PublishingEnvironmentNeutralityValidator`, an `EnvironmentNeutralRules`/`PackageArtifactScanner` rule engine, and a DRV `EnvironmentNeutralValidationStage` all already existed and already used `${AOVIAS_*}` deployment variables exclusively. No M1.4 report existed, and — critically — **the test project did not compile**: four existing test files called a `ComposeGenerator` constructor overload that no longer existed, because a prior edit had already removed `ComposeGenerator`'s dependency on `PublishingSettings` (the actual environment-neutrality fix) without updating its callers. That left the sprint's own regression suite unable to run at all.

This sprint's real contribution is therefore threefold: (1) a full artifact-by-artifact audit confirming what was already neutral versus what still needed proof, (2) fixing the build-breaking regression and a second, more subtle correctness bug found during that audit (the neutrality gate inside `ComposeGenerator` was validating against `context.ComposeContent` *before* that field was assigned, so it silently never scanned the compose file it had just generated), and (3) closing the two genuine gaps the audit found: no regression evidence that the *same* package is portable across more than three environments, and no dedicated M1.4 test suite proving the full artifact set together (rather than one generator at a time).

No Release Library, Infrastructure Template, or Runtime Agent code was touched, per scope.

## 4. D2/D3 — Environment Variable Resolution & Compose Neutrality

Verified directly in code (not just by test): a repo-wide search for `profile.ConfigRoot`, `profile.LogsRoot`, `profile.DeploymentsRoot`, `profile.HostConfigRoot`, `profile.DockerNetwork`, etc. inside `Aovias.Publishing/src` returns **zero matches** — nothing in the generation path reads a resolved `DeploymentProfile` value into a package artifact. The one place `DeploymentPathResolver.Resolve` is called from Publishing is `SolutionPublishingPreflightService.CheckPublishProfiles`, which validates that the *publishing machine's own* profile is well-formed (writable directories, valid container paths) as a preflight sanity check — it does not feed any generated file.

The one real defect found: `ComposeGenerator.GenerateAsync` ran its own neutrality gate against `context.ComposeContent` before that field was set, so the gate always evaluated stale/empty content instead of the compose YAML just built. Fixed by assigning `context.ComposeContent` immediately after serialization and before the gate runs, with rollback to `null` on failure so a rejected compose file can never leak into a later stage. This is a hardening fix, not evidence of an actual leaked package — DRV's independent, later `EnvironmentNeutralValidationStage` scans the packaged compose file again after extraction and would still have caught a real violation before certification.

## 5. D4 — Contract Neutrality

Every contract builder in `ServiceContractRegistry` was reviewed. Findings:

- `NetworkContract.NetworkNameToken` defaults to `${AOVIAS_DOCKER_NETWORK}` and is never overridden with a literal value for any of the 10 services.
- `VolumeMountContract.HostToken` is always one of `${AOVIAS_HOST_CONFIG_ROOT}`, `${AOVIAS_HOST_LOGS_ROOT}`, `${AOVIAS_HOST_PACKAGES_ROOT}`, or `${AOVIAS_HOST_DEPLOYMENTS_ROOT}` (runtime-agent only) — confirmed programmatically for all 10 services via a new theory test.
- `FilesystemDirectoryContract.Path` values are always container-internal absolute Linux paths from `PlatformRuntimeDefaults`/`PlatformDeploymentDefaults` — never a host path.
- `InfrastructureContractBuilder.Build` (the unified `infrastructure.contract.json` model) declares required resources, capabilities, and provider expectations (RabbitMQ, Azure Service Bus, Azure OpenAI, Nginx) with no customer-specific endpoints or credentials — it is fully declarative, it is simply not yet wired into package output (§3).

Publishing preserves the required separation: contracts declare *what* infrastructure a service needs, never *where* it will run.

## 6. D5 — Ownership Matrix

| Concern | Owner | Evidence |
|---|---|---|
| Compose/env placeholder names (`${AOVIAS_CONFIG_ROOT}`, `${AOVIAS_DOCKER_NETWORK}`, etc.) | **Publishing** | `ComposeDocumentBuilder`, `DeploymentEnvironmentTemplate` — a fixed, versioned set emitted identically every publish |
| Contracts (volume/filesystem/network/health/dependency/service-manifest/infrastructure) | **Publishing** | `ServiceContractGenerator` / `ServiceContractRegistry` — declare requirements, never environment values |
| Deployment profile values (host paths, docker network name, `DOTNET_ENVIRONMENT`) | **Deployment** | `aovias-config/profiles/{name}/settings.deployment-host.json`, resolved via `DeploymentPathResolver` |
| Runtime substitution of `${VAR}` into a concrete `.env` | **Deployment** | Runtime Agent, at deploy time (out of scope for this sprint per "Do NOT redesign Runtime Agent deployment execution") |
| Secrets | **Deployment** | Publishing only ever emits `${PLACEHOLDER}` tokens for secret-shaped configuration keys (`DeploymentArtifactSanitizer`/`ConfigTemplateGenerator`); actual secret values live in the deploy-time secrets directory, never in the package |
| Deployment paths (`AOVIAS_HOST_*`) | **Deployment** | Same as profile values above |

No overlap found: Publishing was verified (§4) to never read a resolved profile value into an artifact, and Deployment-side code (`DeploymentPathResolver`, `DeploymentHostSettings`) has no dependency on Publishing assemblies.

## 7. D6 — Package Portability Validation

A QA profile (`aovias-config/profiles/qa/settings.deployment-host.json`) was added with deliberately distinct values — `Staging` environment, host roots under `/srv/aovias-qa/...`, docker network `aovias-qa-network` — specifically so portability could be demonstrated against more than the pre-existing demo/uat/production set, which happened to share identical docker network names and mostly-identical host roots.

Verification performed (all as executable tests, §8, since no live Docker/VPS targets are available in this environment):

1. **Same generated bytes regardless of publisher profile** — `Generated_compose_and_templates_are_identical_regardless_of_publishing_machine_profile` builds the compose file, `.env.template`, and `config-template.json` for the same service with `PublishingRequest.Profile` set to `demo`, `uat`, `qa`, and `production` in turn, and asserts byte-for-byte equality against a `demo` baseline. This is the direct proof that publishing does not require rebuilding per target environment.
2. **Profile resolution across all four environments succeeds and only expected values differ** — `EnvironmentComparer.Compare(configRoot, ["demo","uat","qa","production"])` reports `IsConsistent == true`; only host paths and docker network name differ, everything else (container-side paths, profile/secrets directory names) is identical.
3. **QA profile itself resolves safely** — `DeploymentPathResolver.Resolve` succeeds for `qa` and the resolved host paths contain no developer/personal path fragments.

Remaining blocker (documented, not fixed in this sprint — out of scope): there is no live Docker/VPS target reachable from this environment, so "deploy the same `.aovdeploy` file to four running hosts" could not be performed end-to-end. The verification above proves the package *content* is identical and that profile *resolution* succeeds for every target; it does not exercise the Runtime Agent's actual bind-mount/container-start behavior on a real QA host, which is explicitly out of scope ("Do NOT redesign Runtime Agent deployment execution").

## 9. Build Verification

No .NET SDK is available in this sandboxed environment, and outbound network access to install one (`dot.net`, NuGet, apt) is blocked (403 on every attempt). `dotnet build`/`dotnet test` could not be executed here. In place of a live build, verification was done by:

- Reading every type, interface, and constructor referenced by every line changed, confirming signatures match exactly (this is how the `ComposeGenerator` constructor break was found in the first place).
- Re-reading each edited file in full after editing to confirm brace/paren structure and that no dangling `using` directives or orphaned helper classes remained.
- Cross-checking the new QA profile JSON parses correctly and satisfies every field `DeploymentHostSettings` marks `[Required]`.

**Action needed on a machine with the .NET SDK:** run `dotnet build Aovias.PublishingEngine.slnx` and `dotnet test Aovias.Publishing/tests/Aovias.Publishing.Core.Tests` before merging. Given the nature of the fix (a genuine pre-existing compile break), this is not optional — it is the first real build/test run this branch will have had.

Deterministic publishing (M1.2) and contract-driven generation (M1.3) were not architecturally touched: `DeterministicPackageFingerprint`, `FingerprintPolicy`, `PublishingBuildIdentityService`, and the M1.3 metadata-driven generators are untouched by this sprint's two source changes.

## 11. Readiness Assessment

**Ready for the next milestone (Release Library & Artifact Lifecycle unification, per both the governing spec and the M1.3 report), pending a real build/test run.**

What this sprint confirmed is genuinely in place: the pipeline never bakes a host path, hostname, IP, or hardcoded Docker network name into a package; every host-dependent value in every generated artifact is a `${AOVIAS_*}` reference; contracts declare requirements, not infrastructure; and the same generated bytes result regardless of which profile is active on the publishing machine. What remains open, unchanged by design: the Release Library's dual import paths (CSM flat copy vs. category-folder organizer) and the still-unwired `infrastructure.contract.json` — both already scoped to later milestones and untouched here.

**Blocker before merge:** run `dotnet build` and `dotnet test` on a machine with the .NET SDK. The fixes in this sprint make that possible for the first time in this branch's history; it has not yet been confirmed to actually pass.
